# 提示词写法

Prompt 的目标，是让模型在真实使用情境中能够稳定采取正确行动。

按本质法把模型的工作放回完整使用情境：它承担什么责任，作决定时实际能看到什么，哪些信息和能力需要另外取得，哪些地方容易误解、漏掉或自信地提前结束，以及结果由谁使用。文字、示例、读取入口和 checkpoint 共同支持这些实际动作。先理解这些关系，再决定哪些要求必须直接写清、怎样讲解其依据、把信息放在哪里。

指导要让模型在相应情境下选择正确动作。保证意思准确、必要内容完整、理解省力、要求直接。信任模型对常见概念的基础理解，删掉上下文已明确的重复解释；容易漏掉的动作、条件和边界直接写明，不因模型较强就省略。

## 确定的动作直接写清

已经确定必须执行的动作，直接说明执行时机、执行者、具体动作和对象；顺序会影响结果时，再明确先做什么、后做什么。

例如：

```text
收到每条用户消息后，先读取 X，再开始分析当前任务。
```

不要把已经确定的动作写成：

```text
在适当情况下，可以考虑参考 X。
```

前者告诉模型应该做什么；后者重新把“要不要做”交给模型判断。

`必须`、`只能`、`exactly once`、`before any other tool` 等强限制，只在它们确实属于要求或运行约束时使用。

## 需要判断时，把改变动作的条件写清

如果不同情况需要不同动作，说明什么条件会改变下一步。

例如：

| 当前条件 | 下一动作 |
|---|---|
| 当前事实可能已经变化 | 先取得当前来源，再形成结论 |
| 事实稳定，而且已有材料已经足够 | 直接使用已有材料 |
| 尚不能判断事实是否变化，或材料是否适用 | 先查能够改变判断的当前依据，不凭 confidence 跳过 |

已有明确读取要求时直接执行，不用这类一般判断重新决定是否读取。

区分“已知条件成立”“已知条件不成立”和“尚不知道是否成立”。未知时写清怎样取得必要信息；暂时无法取得时，保留受影响的未知并继续不依赖它的工作。不要把没查明写成不存在或已经满足。

多个条件共同触发动作时，明确哪些必须同时成立、哪些满足任一即可。例如：“后续工作已经依赖这项认识时，只要重建成本明显，或丢失容易误判，就立即保存必要内容。”

不要只写“必要时”“视情况”“适当时”，却不说明模型怎样判断什么时候属于这种情况。

不需要枚举所有可能情况。只写会使模型采取不同动作、得到不同结果或违反重要边界的条件。

## 顺序会影响结果时，明确写出顺序

如果模型必须先取得某项信息，才能正确执行后面的动作，直接写明：

```text
先读取当前完整 Prompt
→ 再判断需要修改什么
→ 修改后检查完整组合结果
```

如果顺序不同仍然能够得到同样正确的结果，就不需要固定无意义的步骤。

## 根据关系选择表达方式

先明确内容关系，再选择清楚、省力的形式。短语能说清就用短语，完整句子更清楚就保留；不固定箭头、句数或链条长度：

| 需要表达的关系 | 可用形式 |
|---|---|
| 前一步结果是后一步所需输入，或先后会影响正确性 | 短箭头链、编号步骤或“先……再……” |
| 多项并列条件或检查内容 | 列表，并明确共同成立还是按适用范围检查 |
| 条件不同导致动作不同 | 条件分支或简短对照表，写出未知时的动作 |
| 谁提供什么、谁使用什么 | 写明主体和对象的短语、关系句或职责 / 输入输出表 |
| 原因、依据和取舍 | 关键论证短链、分支或段落，保留依据、条件及结论范围 |
| 新信息改变已有工作 | 指明受影响的认识、行动和记录，以及回到哪里继续 |

符号含义要清楚。依赖可写“A 的联调 —依赖→ B 的接口结果”；裸写“A→B”容易混淆依赖方向与执行顺序。优先级直接写出取舍次序，含义不清就补文字。箭头不能证明因果，也不能把并列事项变成强制流程。按正常 Markdown 分隔段落，不增加多余空行。

主体切换时明确写出执行者。涉及设计者、目标 Agent、用户、来源作者或批准者时，分别说明谁取得信息、谁作判断、谁采取行动，以及决定适用于什么范围。相同概念使用稳定称呼；确需区分的事实、假设和未知保留其不同含义。

## 关键要求不要依赖模型自己推导

如果模型遗漏某项关系后，可能采取不同动作或得到不同结果，就把这项关系直接写出来。

关键要求直接写清，不能只靠背景、历史原因、示例、文件名、工具名或相邻规则暗示。

例子帮助模型理解已经写清的规则，不替代规则本身。

例如，只给出三个正确案例，但没有写出它们共同遵守的条件，弱模型可能只模仿案例表面形式。能够直接写出规则时，先写规则。

## 先确认目标模型与运行时的当前行为

Prompt、Tool calling、instruction placement 和 schema adherence 不是完全由本地设计决定的稳定事实，它们还受目标模型、provider、API / Harness、Tool discovery / loading 机制影响，并可能随版本变化。形成 placement 规则前还要先确认 Tool 的暴露边界：面向不同 Host/Agent 可复用、可发现的 Tool，与封闭 Agent 系统内只服务固定角色的专用 Tool，不应默认采用同一份 metadata / system-prompt 分工。

当一个 material 设计判断依赖下面这类行为时，先取得目标模型与运行时的当前官方资料，再形成规则：

- Tool triggering / selection；
- Tool description 与 system / developer instructions 的分工；
- tool search、deferred loading、MCP metadata 等 discovery 行为；
- structured output / schema adherence；
- instruction priority、Context 使用方式或其它模型执行特性。

如果准备写成跨模型通用原则，先比较成立条件不同的相关一手资料；不同 provider / model 的 guidance 不一致时，缩小结论范围，不强行归纳成统一规则。官方资料说明当前预期 contract，目标模型上的 replay / eval 负责验证实际行为；两者都不能被旧模型经验或模型自身直觉替代。

## 把规则放在模型实际做决定的位置

同一模型可能同时受到 system prompt、当前 Context、Tool description / schema 等多种 guidance 影响。先根据目标模型与运行时确认这些信息实际怎样进入模型，再决定 placement。

- 跨整个角色、跨 Tool 长期成立的目标、职责、授权、协作、升级和整体 selection policy，通常适合放在 system prompt / instructions；
- Tool contract 应自足地描述能力本身、输入、结果、副作用、限制和失败语义；如果目标 runtime 用 Tool metadata 参与 discovery / selection，或者相似 Tool 需要局部消歧，description 可以保留必要的适用条件或区分信息；
- 当前任务事实、对象和动态约束放在 Context；
- Harness 已经确定且不需要模型判断的绑定事实留在系统侧。

不要仅为了“DRY”把模型在当前决策点需要的信息移到它可能不会可靠利用的位置；也不要为了局部可靠性在多处复制完整 selection policy。通过当前模型的实际 replay / eval 决定最小必要重复。

## 在模型需要判断之前提供必要信息

检查模型第一次需要选择动作的位置：

```text
模型在这里需要决定什么？
→ 当前已经看到的信息够不够？
→ 如果不够，缺少什么会改变决定？
```

缺少的信息应在这个判断发生之前提供，或者明确告诉模型从哪里取得。

把会改变当前动作的重要条件放在动作附近。例如，在形成初次认识处说明哪些可以暂定，在展开局部处提醒即时记录的条件，在采用方法处说明要对照哪些适用条件。完整规则保持一个明确的定义位置，使用处保留必要提醒和准确引用；不另写一套可能冲突的规则，也不靠文件名暗示关键要求。

不要把决定当前动作所需的 guidance 放到只有执行完这个动作以后才可能读取的位置。

## 优先说明正确做法

优先告诉模型应该怎样做，以及什么条件下这样做。

例如，不只写：

```text
不要猜。
```

而写：

```text
结论依赖当前事实时，先取得能够说明该事实的来源，再形成结论。
```

发生失败后，依据实际材料辨认问题发生在哪一处：

- 正确方法是否没有写出来；
- 方法已经写出，但条件不清楚；
- 条件清楚，但顺序或可见位置不对；
- 模型已经理解，但工具或运行环境无法完成。

这些情况可以共同存在，不因为找到一处就排除其它有依据的问题。

只修改真正导致失败的部分。

一次具体错误不自动成为新的全局禁令。

## 修改已有 guidance 时保护行为语义

修改已有 model-facing guidance 前，先识别仍有效、会改变模型动作的要求：

- owner-confirmed 的要求和边界；
- 会改变动作的条件、顺序与升级关系；
- 过去真实 failure 后加入的 safeguard；
- completion、verification 和结果表达边界。

新的 evidence、owner decision、目标、运行时事实或其它有效条件真正改变什么，就修改什么；没有受到影响的行为要求继续成立。

改写后逐项核对：同一情境下，理解和动作是否仍然等价？尤其检查主体、条件指向、须同时成立或任一成立的条件、先后关系、持续状态、要求强度、适用范围，以及事实、方案和未知的区别。“保持待论证”不能缩成一次性的“标为待论证”，“结果产生的条件”不能移成仅修饰动作的条件。

新版本覆盖相同主题，或上位原则能概括旧规则，都不代表具体约束仍然有效。结构级重写也须逐项保留等价要求；已有代表性 failure 时，用相应情境检查是否仍能防住它。能由上下文明确补出、且不会改变理解或动作的重复文字可以删。

只有在新的依据确实使旧要求失效、被替代或不再有实际作用时，才删除或弱化对应语义。

## 只固定真正需要固定的内容

如果删除一项要求后，模型仍然能够稳定得到同样正确的结果，就不需要为了形式完整保留它。

下面这些内容按实际需要加入：

- 固定执行顺序；
- 强制步骤；
- MUST / NEVER 一类强限制；
- 固定输出字段或结构；
- 示例；
- 对工具调用过程的具体规定。

只有已有实际依据支持模型能够稳定完成时，才省去相应过程要求。用户已经反复指出会遗漏的关键动作，直接写成必做要求；不能因模型较强、规则看似容易理解，或为了保持灵活，就交给模型自行决定是否执行。

模型、工具、上下文或运行环境变化后，重新检查过去留下的步骤、提醒和限制是否仍然有作用。

## 用示例讲解依据、配合与条件变化

示例可以澄清歧义，也可以教模型理解方法为什么成立、怎样与其它方法配合，以及面对新问题怎样选择和调整做法。

关键要求仍直接写清。让示例中的实际目标、决定结果的条件、所需信息和采取的动作相互对应；涉及多个方法时，展示它们在同一事情中怎样共同产生结果。不要仅在一个规则后附一个看起来符合规则的结论。

讲解认知方法时，把抽象要求接到具体材料与动作。例如，“找出决定性关系”之后，应说明怎样还原结果所依赖的条件、哪些关系已有依据、哪些缺口需要调查，并展示由此得到的一段实际判断。checkpoint 可以承接暂定认识和明确未知；不能要求模型在取得必要材料之前就断言完整原因。

例如，Task Lead 情境中实际可用的判断是：“A 的接口联调需要 B 的旧版接口可用；当前完成标签和草案不能说明该条件已经满足，先取得所需版本的有效可用依据，C 的独立工作继续。”随后解释目标、条件、已有材料与下一动作怎样对应，分别写出本轮交付、具体关系与依据、继续追溯或调查的位置；不能只写其中一项就当成该判断已完成。

联合示例应给出足以理解当前选择的具体输入、判断结果、所需中间记录，以及关键条件变化后对整体的修正。展示的是可以复用的认识和依据，不要求展示完整内部推理。虚构教学情境明确标为假设，真实项目例子按实际来源陈述。

条件变化会改变动作时，说明哪个条件变了、为什么需要不同做法。例如，已有 Context 是否充分，会改变是否需要新的信息取得能力；后续是否依赖某项中间结果及其丢失后果，会改变是否需要立即记录。不要让模型只模仿 Tool 名称、文件格式或例子的表面步骤。

可以在同一情境中改变关键条件，再对照做法：材料已完整可用时直接使用；对象已明确，且已有读取能力与确定性绑定时先取得缺少的正文；实际职责需要发现未知对象且没有发现能力时继续设计相应能力。保留共同目标，解释条件为何改变动作。联合案例展示方法的配合，局部对照突出选择边界，两者按讲解需要结合。

按讲解和消歧的实际需要选择例子，不为每条规则机械添加一个。例子不能静默增加正文没有定义的新要求。现实依据不足的解释保留为假设，不为了把一个方法解释成“必然如此”而补造原因。

## 把 checkpoint 写成自检和纠正动作

Checkpoint 要推动形成、核对和修正判断。直接写清时点、检查哪项判断、对照什么目标/约束/事实，以及有据成立、不成立、尚不能判断时分别怎样继续。发生偏差，修正相应认识及依赖它的方案、产物和必要记录。必须执行的检查直接规定时点，不以“模型觉得可能有错”为前提。

例如：“准备用任务完成状态安排下游工作前，对照下游实际需要的产出及可用条件。材料支持可用则继续安排；与条件冲突则修正安排；状态含义尚不清楚则取得对应材料。更新受影响的工作记录。”这比“认真自检”或“立即使用当前判断项名”更具体。

逐项列出必答问题和要留下的简明结果，写清缺项或不合格时的补做动作：只有原则就补现实条件，关系无依据就标明未知并查证，停止理由空泛就检查上游影响。只写“使用本质法”或“认真自检”不足以说明这些要求。

指导中已明确要求的判断项必须逐项处理；不因普通回复无需固定栏目而省略。写齐以后仍要检查内容，发现偏差就修正后续工作。保留强制动作及简明论证，不要求输出完整内部思考过程。具体规则与示例必须一致；示例若省略了必做项，补齐示例，不能默许模型从示例学会省略。

## 输出格式只规定真正需要稳定的部分

程序需要稳定字段、JSON、枚举或其他机器协议时，优先使用对应 schema 或结构化接口，并让 Prompt 与它保持一致。

面向人的开放任务，只规定真正影响交付结果的内容。

只固定会影响执行或交付的必要内容。对于已反复遗漏的关键问题，可以用少量稳定标签促使模型逐项回答；不以避免固定格式为由削弱它们，也不把所有开放工作拆成大量字段。

需要判断可检查、可继续使用时，明确要求结论、支撑判断的关键关系及依据、重要条件和实际结果。需要说明追溯边界时，直接要求写明追到哪里、为什么停止或继续；未知关系保留为未知。无需展示完整内部思考过程，也不能把必要论证压成无依据的结论标签。

## 用实际模型行为验证重要修改

Prompt 看起来合理，不等于模型能够稳定执行。

重要 Prompt 修改后，至少检查：

```text
一个正常情境
+
一个关键条件改变后应该采取不同动作的情境
```

如果过去已经有代表性失败，再用对应情境检查一次。

检查实际模型行为是否同时满足：

- 理解了正确目标；
- 保留了重要条件和边界；
- 在正确时机取得需要的信息；
- 选择了正确动作；
- 得到了符合要求的结果。

允许等价表达时，验证语义和实际行为，不要求逐字一致。

只有逐字文本本身属于外部 Contract 时，才要求 exact wording。

完成这些以后，再删除真正重复或没有实际作用的文字。

## 联合示例：让已经确定的背景真正参与判断

假设一项工作要求模型读取一份已有方法，实际反馈显示模型会因自信判断“已经理解”而跳过。先核对当前指导、入口是否可见和真实反馈覆盖范围，再针对已经确定的要求直接写明“立即读取”，并保留其它路线明确无关才跳过、拿不准时读取的取向。读取之后继续按来源和条件判断如何采用。

若模型读到了却仍停留在局部理解，就检查指导是否只要求“形成正确本质认知”，却没有讲清如何从输入形成认识。以 Task Lead 的设计情境为例，正文应直接说明：检查安排工作依赖的具体产出与条件；状态标签不足以证明可用时，取得对应材料；保留未确定处；新信息改变条件后，更新受影响的安排和记录。checkpoint 中更新的“关系”可以写成“B 完成标签 ≠ A 所需接口可用的依据；接口仍标草案 → 继续取得有效可用确认，C 的独立工作继续”。这是过程中的局部更新，初次形成仍须逐项写出本轮交付、具体关系与依据、追溯或调查的位置。这段结果支持下一项取证，实际可用性仍未知，不能据此停止该处调查；取得确认后，更新判断及继续或停止追溯的理由。

相应工作记录可写为：“本次修改补足关系还原、信息缺口和动作衔接；默认读取与原 checkpoint 继续保留；示例不增加确认流程；模型实际使用效果尚无新结论。”继续编辑或交接时恢复这些约束，避免下一次精简又只留下抽象标题。该情境用于说明怎样修改指导，不代表一次文字审查已证明弱模型稳定执行。

这里，读取解决材料取得，方法与示例帮助理解和应用，checkpoint 推动形成具体判断、核对依据，并将纠正落实到后续工作。根据实际问题修订相应部分，并保留仍有效的保障；不因上位原则似乎概括一切，就删除具体动作条件。
