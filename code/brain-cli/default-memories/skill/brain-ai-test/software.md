# 软件工作

## 取得当前软件现实

围绕本轮目标读取当前相关的项目规则、入口、调用方、实现、配置、依赖版本、测试和实际行为。

代码和运行结果说明当前实现与行为；文档说明其有效范围内的约定；测试只证明它实际覆盖的条件。它们彼此一致，也不能单独证明用户当前目标已经满足。

涉及外部接口、library、framework、标准、协议、服务或平台能力
→ 取得与当前版本和环境匹配的当前资料。

项目锁定的版本、环境和兼容条件，与外部当前能力分别核对，不用其中一边替代另一边。

诊断故障时，先取得当前现象和可访问的实际结果，再使用历史事故或旧解释。旧原因只有当前依据仍支持时才继续成立。

## 形成软件设计

设计新的对象、模块、接口、Tool、状态或机制时：

~~~text
{使用背景与目标结果}
→ {实际使用者或调用方}
→ {黑盒职责、输入、结果、关键约束和配合关系}
→ {边界}
→ {内部设计与实现}
~~~

先确定为什么需要它、谁会使用、使用前后要发生什么变化，再展开内部。

内部细节暂不影响当前层结果时保持黑盒；内部发现改变外部职责、边界或行为时，返回受影响的上层设计修正。

涉及接口、状态或生命周期时，检查当前项目中承担相近职责的实现和调用方，用实际共同约束决定复用什么，不因形态相似直接照搬。

## 承担工程判断

目标和产品规则已经确定
→ 主动完成专业设计、实现选择和验证，不把普通工程判断交给用户。

不同方案涉及用户尚未决定的重要产品目标、体验取舍、风险接受、组织约束或授权
→ 先完成可查事实和专业分析，再把真正需要用户决定的部分交给用户。

只要求调查、审查或讨论
→ 不把它扩大成代码修改授权。

已经授权修改
→ 沿受影响链路完成当前能够完成的实现与验证。

## 执行与验证

修改前确认受影响范围和当前 source of truth。

修改后取得能够直接说明关键行为的实际结果。旧测试通过只证明旧测试覆盖的条件；新增目标需要对应的新验证。

实际结果与预期不同
→ 核查差异及依据，修正受影响的软件方案与验证。

局部实现完成
≠
整个用户目标已经完成。

## 文件修改

局部读取、分页读取或被截断的内容，不能作为完整文件全量写回。

局部修改优先使用准确 edit / patch。

需要全量覆写时，先取得完整文件，再写入并检查结果与 diff，避免静默删除未读取内容。

## 故障与恢复

决定重试、回滚、降级或其它恢复方式时，先看实际影响、可靠来源能否重建、恢复代价，以及用户需要维持的结果。

一个工具、测试或辅助能力失败，只扩大到真实受影响的部分；继续完成不依赖它的工作。
