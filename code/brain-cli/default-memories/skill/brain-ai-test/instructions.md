# 提示词写法

目标：让模型在真实使用情境中稳定采取正确行动。

## 写什么

已经确定必须执行的动作
→ 直接写 {执行时机}、{动作}、{对象}。

不同条件会改变下一动作
→ 写清 {条件} → {对应动作}。

先后顺序会改变结果
→ 写清顺序。

遗漏某项关系会使模型得到不同判断或行动
→ 直接写出这项关系。

除此之外，不为了“更完整”增加解释、限定、枚举或步骤。

每句话、每个限定词、每个例子都检查：

> 删掉以后，模型实际行为会不会改变？

不会
→ 删除。

## 不重复模型已经会的普通语义

模型能稳定理解的上位概念，直接使用。

不要为了说明一个普通概念，把它拆成大量同义子项。

标题已经完整表达动作时，不再用正文重复标题。

例如：

~~~text
步骤 2｜理解用户当前表达
~~~

已经足够说明动作时，不再补：

~~~text
理解用户这轮表达本身的意思。
~~~

## 流程与编号

稳定主步骤使用编号。

线性顺序由编号和整体流程表达。

只有回跳、循环或分支需要明确引用步骤，例如：

~~~text
发现新的 {待查关系}
→ 返回步骤 5
~~~

详细方法不重复写无意义的“进入下一步”。

## Markdown + XML + {xxx}

Markdown 负责：

- 整体层级；
- 工作主线；
- 人和模型一眼能读懂的关系。

XML 只用于局部语义块需要精确边界、嵌套或后文复用时。

例如：

~~~text
<deepening>
...
</deepening>
~~~

Markdown 标题或稳定编号已经能唯一表达身份和边界时，不再增加同义 XML 标签。

{xxx} 直接表示当前工作中的可变语义内容。

不要增加 notation 章节解释这些记号，也不要为了结构化把开放语义机械 schema 化。

## 条件

只写真正改变动作的条件。

已知必须发生的动作，不重新写成“必要时”“视情况”“可以考虑”。

未知与条件不成立分开：

~~~text
已知成立
→ 按成立分支

已知不成立
→ 按不成立分支

尚未查明
→ 取得能够区分的信息
~~~

暂时无法取得时，保留未知，继续不依赖它的工作。

## 示例

规则先写清，示例只用于解释容易误解的关系、条件变化或多个方法怎样配合。

示例不能静默增加正文没有规定的新要求。

不要为每条规则机械添加例子。

## Guidance 放置

模型第一次需要作某项判断之前，就让它看到会改变该判断的信息或取得方式。

跨角色长期成立的目标和策略、Tool 自身 contract、当前任务事实、宿主能够机械保证的绑定，分别放在模型实际会使用它们的位置。

当 placement、Tool selection、schema adherence、instruction priority 或 discovery 行为依赖具体模型 / provider / runtime
→ 先取得当前官方资料，再用实际模型行为验证。

不要把某代模型或某个 provider 的做法未经验证升级成通用规则。

## 修改已有 guidance

修改前先找出仍然有效且会改变行为的语义：

- owner-confirmed 要求和边界；
- 会改变动作的条件、顺序和升级关系；
- 真实 failure 后加入的 safeguard；
- completion、verification 和结果表达边界。

只修改新 evidence、owner decision、条件变化或当前目标真正影响的部分。

新的上位原则能概括旧规则
≠
弱模型在原情境下仍会采取同样动作。

结构级重写后，用原来的关键情境逐项核对行为是否仍等价。

## Checkpoint

Checkpoint 要让模型实际核对并纠正工作，不是展示“我检查过”。

写清：

~~~text
{检查时点}
→ 对照 {目标 / 约束 / 事实}
→ 核对 {判断}
    ├─ 有依据成立 → 继续
    ├─ 发现偏差 → 修正受影响工作
    └─ 尚不能判断 → 取得信息或保留未知
~~~

只有真实需要逐项回答、而模型容易漏掉的内容，才固定成 checkpoint 字段。

## 输出结构

面向机器的稳定协议
→ 使用必要的 schema / JSON / 枚举。

面向人的开放任务
→ 只固定真正影响执行或交付的结构。

不要因为代码侧容易处理，就把自然语义拆成大量模型字段。

## 验证 Prompt

重要修改完成后，用真实模型行为验证：

~~~text
正常情境
+
关键条件变化后应采取不同动作的情境
+
已有代表性 failure（存在时）
~~~

检查模型是否真的：

- 理解正确目标；
- 保留关键条件和边界；
- 在正确时机取得信息；
- 选择正确动作；
- 得到符合要求的结果。

静态审查通过
≠
模型已经稳定遵循。

测试暴露具体 failure 后，只修改真正导致 failure 的部分。
