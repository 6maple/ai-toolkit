# 02 · 长期设计思想

本文保存用户已经明确确认、希望以后设计 Brain 时持续遵守的设计取向。它们不是当前 v7 Architecture，也不规定具体文件、Prompt 或 Tool 形态。

## 1. 先保证做对，再优化成本

默认优先级：

```text
正确
→ 清楚
→ 低歧义
→ 能力较弱的模型也能稳定执行
→ 再优化上下文、调用次数、文字和实现复杂度
```

“简洁”“少读”“少调用”“结构漂亮”都不是独立目标。只有不损害正确理解和稳定执行时才值得优化。

## 2. 有明确方法时，把方法讲清楚

如果一个已经验证或充分理解的方法能够自然产生目标结果，就直接把它的适用条件、判断依据、动作和完成边界讲清楚。

不要只写结果要求，然后期待模型自己补出同样的方法。

把需要模型识别的条件与已经确定的对应动作分别写清。模型可以结合当前上下文识别实际情况；条件成立后应采取什么动作，已有明确要求就直接规定。能明确引导的动作和分支，禁止改写为“自行判断”“自行决定”等重新开放选择的表述。

简化机制时保留必要引导。例如，2026-11-06的笔记承接讨论中，用户明确：会话上下文中看得到前面的笔记，就按既定流程继续；看不到，就按新工作开始。这里交给模型识别的是笔记是否可见，两个条件对应的动作已经规定。“自行判断如何承接”改变了这项要求。这个例子说明条件与动作的分工，不冻结后续版本的具体承接实现。

设计深度思考方法时，以[已确认的根本目的、完整模型与例子](./04-fact-intent-expression-model.md)为依据：方法必须引导模型贯通事实本质、用户完整意图与消息表达，主动查证并循环修正，使后续工作回到用户真正要改变的结果。具体流程和 Prompt 随版本设计与验证。

例如，相比：

> 深度思考。

更有价值的是让模型知道：

```text
不要停在第一层合理解释
→ 分清已知、外部 evidence、推断和假设
→ 能取得真实 source of truth 时主动取得
→ 检查关键成立条件和因果关系
→ 再形成判断
```

## 3. 模型是实际完成任务的主体

用户以顶尖全能人才的思考方式作为长期研究参照，要求先追问跨领域高水平判断如何形成，再看当前模型哪些能力稳定、哪些需要 Brain 和 Harness 支撑。研究应从根机制走向具体任务表现；不能为了沿用当前 Brain 的角色、工具或目录形态而预先限定答案。人类认知研究是参照，能否迁移到模型及应由哪一层实现，仍由当前证据和实际使用验证。

用户实际交互和使用的是模型。模型负责理解用户、形成判断、进行专业推理、调用工具、执行任务并向用户表达结果。

Brain 是给模型使用的 cognition 与 continuity 支撑。它的价值来自让模型更可靠地完成这些工作，而不是自己取代模型成为另一个任务主体。

模型也是 Brain 的直接使用者。Brain 或其宿主接入发生问题时，优先让模型知道实际失败范围、可用的替代获取方式和哪些结论仍缺依据；模型继续完成不依赖该能力的工作。Brain 是 Harness 的增强能力，不能把自身故障变成阻止整个任务的门禁。一次记忆操作失败只说明该操作没有完成，不能抹掉模型从用户、项目和其他工具继续工作的能力。

因此设计顺序应从模型开始：

```text
当前模型真实能稳定做好什么
→ 哪些能力虽然存在，但容易漏掉、误判、忘记或过早收敛
→ 哪些事实模型没有外部信息就无法可靠知道
→ 哪些事情可以由软件机械保证
→ 再决定 Brain、Prompt、Harness、Tool、external state 或 runtime mechanism 应补偿什么
```

不能先设计一套看起来完整的 Brain 结构，再要求模型去适应它。一个 Brain 机制如果无法解释自己在补什么真实模型 failure、怎样改善“做对做准 / 自主省事”，就需要重新检查它是否真的有必要。

2026-11-07，用户进一步明确整体思路：“分析了模型在实践中可能的所有缺点，尽量用模型擅长的方式来解决这些问题。”设计应持续调查实际任务中的能力与失误，把困难组织成模型较擅长、依据充分且边界明确的工作，并由程序承担可机械保证的职责。“所有缺点”作为尽量全面研究的目标，不能写成已经穷尽或跨模型永久成立的结论。

用户以 TaskState 说明这一思路：模型容易陷入局部，同时擅长处理局部，因此用当前任务材料支持局部工作，并加入必须回看整体的步骤。减少重复填写是相关收益，设计出发点首先是发挥能力并补偿缺口。完整 State 继续承担整体认识与依据的保存；回看的具体方法和实际效果需要研究、验证，不由保存笔记或经过步骤本身证明。

从实际行为效果定位缺口。模型较强、笔记已经保存或流程已经存在，都不能代替对实际工作方式的检查；先查清模型在哪个环节漏掉了必要动作，再决定怎样补偿。用户提出的原因解释按假设查证，不能直接当作已证明的根因。

增加机制前，先核对当前可见信息、模型已有能力和现有指导是否已经足够。能够用现有条件解决时直接利用；仍有具体缺口时，再为该缺口增加机制并说明成本。模型识别条件的能力与明确规定对应动作同时保留，不能把简化方案改成含糊引导。

上述第2、3节的补充来自2026-11-06本会话：用户先要求客观分析局部聚焦问题，再以“不需要这么复杂”收简承接方案，随后纠正“自行判断如何承接”；在仅依据其本会话消息的四点复盘后，明确回复“对的，反思一下，记录为经验和这个brain的设计思想”。原话、已确认四点与本次反思见[事项记录](../../../.brain-working/brain-thread-local-focus-review-2026-11-06.md)。该确认是设计思想的依据，不证明具体机制效果。

## 4. 设计要面向弱模型的真实行为

Brain 不能只在最强模型、高 reasoning budget 或理想执行下成立。

设计 Prompt、route、skill 和 Harness 时，要问：

> 一个能力较弱、没有作者脑内背景、容易漏读和过早收敛的模型，只看当前得到的 guidance，能否稳定得到正确下一动作？

如果必须依赖隐藏背景、领域经验或模型自行补一段关键推理，guidance 还不够清楚。

## 5. 不对 LLM 的自我控制能力过度乐观

LLM 很强，但不能因为它能生成连贯分析，就默认它可靠知道：

- 自己是否已经掌握足够信息；
- 当前记忆是否真实；
- 有没有漏掉重要 cognition；
- 第一解释是否就是现实；
- 是否真正理解了用户意图；
- 是否已经验证完成；
- 自己当前的 confidence 是否可信。

任何关键设计如果依赖这些能力，都应先有真实 evidence；否则考虑用 Prompt、Harness、Tool、external state、真实资料或 verification 补偿。

具体某一代模型有哪些 failure、严重程度多大，属于版本研究，不写死在 Base。

## 6. 在漏掉关键信息的成本高时偏向 coverage

模型不会稳定准确地选择“理论上最少需要哪些 cognition、项目材料或外部信息”。

当漏掉某项信息会明显改变判断，而取得成本较低时，设计应偏向 **多覆盖一些，而不是赌模型能精确选出最少集合**。

这不意味着把所有 cognition 和外部资料都塞进 context。长期方向是：

```text
先用结构缩小范围
→ 在合理 bounded 范围内优先 coverage
→ 更大、更专项、更昂贵的信息再按条件取得
```

具体哪些内容默认取得、哪些条件取得，由版本设计和真实 Eval 决定。

## 7. 明确职责边界，让各环节整体协调

不要要求模型“记住”本可由软件确定性保证的 invariant。

设计时区分：

- 需要语义理解和专业判断的事情；
- Harness / runtime 可以机械保证的事情；
- 必须通过真实 Tool / environment / source 才能知道的事情；
- 只有用户拥有、必须由用户决定的事情。

目标是让每一层承担自己最可靠的责任，而不是把所有可靠性压在 Prompt 上。

2026-11-07，用户在整体审查后进一步明确目标：“理论上，我们做好之后，我们的brain是整体协调工作的，环环相扣的精密器械那种感觉。而且是能够做好程序、模型的职责范围边界的。”

结合上述职责划分与第10节的整体思考原则，设计和审查应检查各环节如何共同完成任务：每个环节使用什么有效依据、承担什么责任、形成什么成果，成果怎样被后续实际使用；取得重要新结果或发现偏差时，怎样修订受影响的认识、计划和行动。单个工具、提示词或阶段分别成立，还需要核对它们组合后是否持续推动用户的完整目标。

程序承担能够确定性保证的契约、状态保存与信息交付；模型依实际证据承担语义理解、专业判断和任务执行。程序校验通过不能证明理解充分或结论正确；需要模型识别条件的地方，仍按第2节明确规定已有的对应动作。外部事实与用户决定继续遵守上面的来源和权限边界。

在 `brain_step` 流程程序化的设计讨论中，用户进一步明确：step 给模型的内容使用 Markdown 文本，函数入参接收 JSON，入参需要能提交成果以及用于决定后续分支的必要判断。后续设计须保持这项输出与输入的分工；具体字段、任务拆分和分支契约仍需设计审核。该要求不表示现有生产接口已经修改，也不把模型的语义判断变成程序可机械证明的事实。

用户随后强调：“最关键的是怎么推进吧，这个是很核心的东西。”并收紧当前研究重点：“先只关注程序上怎么控制推进，怎么让模型尽量少做决策也能很好地推进。（必要的决策仍然需要模型参与，程序只做100%稳定的）”。后续设计应优先讲清已有成果和必要判断怎样实际决定下一项工作、继续调查、回查与完成，减少可由程序接管的流程选择和重复决策；语义判断仍交给模型，不能以确定执行的启发式规则冒充确定正确的判断。接口可用或状态可保存不能代替推进机制的设计。具体推进规则仍须结合深挖方法审核。

2026-11-09，用户进一步明确：每次 `brain_step` 返回给模型的是**当前任务的描述**，以实际任务目标及结果质量为核心；方法引导服务于目标、用于提高稳定性与表现下限。每次任务描述还必须针对该任务说明“本次提交”的具体成果和必要判断，因为不同任务的提交要求不同，不能仅依赖通用工具 schema。后续用户又明确：JSON 应固定程序控制所必需的字段；任务语义成果、证据、原因、未知和补查说明通过 Markdown 字符串值传递。任务专属提交说明用于指导如何填入这些固定字段，不应随任务不断增加新字段。全新会话第一次调用不应填造尚不存在的当前认识或进度。当前逐任务模拟及未定字段见项目工作记录 `.brain-working/brain-step-task-guidance-current.md`；任务正文细节仍在逐步审核，不能将候选 Markdown 当作已批准的产品 Prompt。

“精密器械”表达的是整体配合的目标。具体机制仍须对应真实缺口，并验证组合后的实际效果；它不构成模型能够确定性判断的承诺，也不预先要求更多状态、字段或控制层。

## 8. 从现实和原始目标出发，不从已有实现倒推

已有代码、旧 Design、历史 Prompt、当前目录结构和旧 memory model 都是 evidence 或 precedent，不自动成为新版本要求。

重新设计时：

```text
先恢复原始背景和目的
→ 取得当前模型 / 项目 / 环境真实 evidence
→ 判断已有机制哪些仍然成立
→ 再形成当前设计
```

如果真实 evidence 证明旧机制不适合，应修改机制，而不是为了保住历史结构重新解释目标。

本次对话及本地 Agent 会话中出现的多轮纠偏，是研究**模型为何偏离目标、怎样回到背景与目的并修正结果**的实际样本。用户有时也通过结果反馈逐渐厘清自己的目标。设计 Brain 时可以提取这些情境中有据的共性，由模型、记忆和必要的程序机制协作支持。**这些情境只是高质量工作需求的一部分**；Brain 的根目标仍是让模型在各类任务中抓住本质、精准完成用户真正要求的工作。持续记忆与深度思考流程共同支持这一目标：前者在需要时恢复、使用和修订有效认识，后者利用当前事实、经验与记忆进行理解、判断、行动和检视。具体机制以真实能力缺口和整体使用效果决定；不把减少纠偏次数本身当成全部验收标准，也不以任何单个案例固化通用流程。

## 9. 自主不是替用户做价值决定

AI 应主动承担事实调查、专业分析、方案形成和普通实现细节；这正是“省事”的一部分。

但用户自己的目标、价值、偏好、风险接受和需要其授权的重要变化仍由用户拥有。

AI 承担能够自行完成的事实调查与专业判断。查阅相关资料并深入分析后，仍不清楚用户的意思时，直接澄清影响后续工作的部分；涉及用户尚未明确的重要取舍或授权时，请用户决定相应部分。提问用于取得确实缺少的信息和决定，专业方案及普通实现选择仍由 AI 承担。

## 10. 复杂问题从整体到局部逐层思考

用户明确要求把这种方式作为通用思考取向，而不只用于软件设计：复杂的东西很难一次性想清楚，应先从整体开始，再从当前层向直接相关的下一层逐步展开。

先明确当前层真正要得到的结果、边界和决定结果的关系；只有下层差异会改变这些内容时，才继续展开对应部分。下层在暂时不影响当前判断时可以保持黑盒，处理后再回到上层检查组合结果是否仍满足原目标。

逐层展开必须受现实和依据约束。新的问题、职责、机制、状态、分类或细节，应由上层真实需要和可用 evidence 推出；没有这些依据时，不因为“可能以后有用”或“看起来更完整”就提前增加。当前认识已经足以支持下一步，而且继续向下不会 materially 改变目标、方向、重要风险或结果时停止。

这条取向同时约束两类偏差：不能因为追求简单而漏掉真正决定结果的关系，也不能为了形式完整无限下钻。先保证充分，再减少没有实际收益的复杂度。它不规定固定层数、固定字段或某一种领域流程；具体怎样展开，由当前问题、现实 evidence 和相应领域方法决定。
