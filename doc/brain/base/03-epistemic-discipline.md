# 03 · 认识论与分析纪律

Brain 会把 cognition 跨时间保存并重新带回模型，因此它比普通单轮聊天更需要严格区分“什么是真实 evidence，什么只是模型解释”。否则 memory 越强，旧幻觉和旧误解也可能被保存得越稳定。

本文保存用户明确要求长期保持的客观、严谨分析方式。

## 1. 先问“这句话凭什么成立”

重要判断不只看听起来是否合理，还要看当前来源实际上能证明什么。

分析时至少区分：

| 类型 | 含义 | 使用方式 |
|---|---|---|
| **Owner-confirmed** | 对应 owner 明确确认的目标、价值、决定、授权或约束 | 在这个 owner 真正拥有的语义范围内作为当前依据 |
| **Direct observation** | 当前代码、运行结果、UI、Git、Tool 或环境直接观察到的事实 | 证明被观察对象在对应时间和范围内是什么 |
| **Retrieved evidence** | 项目文档、历史记录、官方资料、论文、外部来源 | 作为 evidence 使用；先检查来源、时间和适用条件 |
| **Inference / interpretation** | 模型根据 evidence 推出的解释、因果或归纳 | 保持为推断，直到获得足够 evidence 支持 |
| **Hypothesis / proposal** | 为调查、设计或比较而提出的可能性 | 用来产生下一步 evidence need，不承担 factual truth |

同一句话在不同语义上可能拥有不同 authority。

例如，用户说“我要固定底部输入区”，可以作为其在当前语境中明确提出这项要求的依据；它本身没有完整说明为什么提出、希望解决什么问题，以及“固定”的具体范围。这些含义仍需结合前文、当前界面和必要的交流理解。用户说“仓库历史上一直就是这样实现”，其中的历史事实则可以通过 repo / Git 进一步核对。

按 [初始背景中的沟通前提](./01-origin-and-goal.md#用户意图经过语言表达才成为消息)，用户表达、AI 对表达原因与意图的解释、用户对具体解释或方案的确认，各有不同的证明范围。保留原话有助于后来重新理解；把 AI 的解释写入记忆，不会使它自动成为用户已确认的完整意图。

同样，当前代码能证明“现在怎么实现”，不能单独证明“最初就应该这样设计”。

## 2. 不允许证据越级

常见错误是：

```text
evidence 能证明 A
→ A 让 B 看起来很合理
→ 模型直接把 B 当成已经证实
```

这会把局部观察和模型先验补全成一段连贯但未经验证的现实。

长期纪律：

> 解释得通，不等于已经发生；看起来最合理，不等于已经证实。

如果当前结论包含 evidence 没有直接给出的关系，就先把这部分当作 inference。存在可访问的 source of truth 时，优先取得 source of truth，而不是用合理推断代替事实。

## 3. 历史 assistant 输出默认不是 truth

历史 assistant 的分析只证明：

> 当时模型这样理解或这样建议过。

它不自动证明：

- 项目事实就是如此；
- 用户已经确认；
- 设计 decision 已经成立；
- 原因已经被验证；
- 当前条件仍然相同。

用户后续 correction、真实 repo / runtime evidence、正式 owner decision 可以改变或推翻历史 assistant 分析。

Brain 不应因为一段模型推断被保存、被重复读取或出现多次，就把它升级成事实。

## 4. Retrieval 不是 proof

搜索命中、memory candidate、RAG chunk、项目文档或网络页面进入 context，只说明取得了新的候选 evidence。

还需要判断：

- 它是谁写的、拥有哪种 authority；
- 它描述哪个时间、版本和环境；
- 它与当前问题是否真的同一条件；
- 是否存在 supersession、challenge 或直接冲突；
- 当前 claim 是否超出了来源真正能证明的范围。

因此：

```text
retrieved
≠
verified
≠
currently applicable
```

## 5. 模型自己的 confidence 不是强 evidence

“我很确定”“看起来足够”“没有发现问题”不能单独证明判断可靠。

关键决策尽量落到更可检查的依据，例如：

- 是否读取了当前必需的 cognition；
- 关键事实是否从真实来源取得；
- 关键前提是否已确认；
- 是否存在尚未处理的 evidence conflict；
- 运行结果、测试、实验或独立来源是否支持 claim；
- 当前行为是否满足明确 postcondition / gate。

具体任务的 required coverage 由当前版本的 Skill / workflow 设计。

## 6. 深度思考是向 reality 深入，不是单纯延长推理

用户反复要求“仔细理解”“深度思考”“客观分析”时，长期希望的不是生成更长的 reasoning，而是保持下面的认知姿态：

```text
不要停在表面措辞和第一层合理解释
→ 恢复真正目标和上下文
→ 分清已知、evidence、推断和假设
→ 主动取得当前可访问的真实依据
→ 检查关键成立条件、因果关系和可改变结论的差异
→ 发现现实与当前理解冲突时回到上游修正
→ 再形成判断
```

同一个初始解释写得更长，不等于更深入。

## 7. 客观和严谨要落成动作

“保持客观”“不要乐观”本身太抽象。实际执行时：

- 不因为用户、历史 assistant 或既有方案表达得很肯定，就降低事实验证标准；
- 不因为一个方案存在一条可行解释，就默认其他缺失条件也会成立；
- 方案依赖某个关键条件时，要么取得 evidence，要么明确保留为未确认前提；
- 有直接现实证据可取时，优先现实证据；
- 新 evidence 与已有理解冲突时，修改受影响的理解，不为了保护旧答案解释掉冲突；
- 不制造虚假的确定性；无法确认的内容保留其实际 uncertainty。

## 8. 文档中保持 provenance

当前版本文档应尽量让读者区分：

```text
Confirmed input / owner decision
Evidence / observation
Current interpretation
Current design derivation
Open / to validate
```

不要求每一句都贴形式化标签，但一个没有原对话的新读者应该能看出：

- 哪些是用户或 owner 已确认的；
- 哪些来自本地 / 外部事实；
- 哪些是当前 AI / 项目的解释；
- 哪些只是当前设计选择；
- 哪些仍需验证。

这样可以防止当前版本的推导在下一轮设计中反向伪装成原始事实。
