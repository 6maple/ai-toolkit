# brain-ai 专业职责与具体例子审核稿

状态：用户已审核并同意三份完整正文；已同步到默认记忆包、实际 Global Brain 与 v7 完整正文记录。模型行为验证由用户人工进行。

## 目标与依据

Base 的目标是让模型在简短消息和长期合作中做对、做准，同时自主、省事。已观察到模型读取现有方法后，仍可能沿第一层合理解释处理任务。近期真实任务中，模型把确认按钮的问题主要解释为现有代码的来源，直到用户纠正才调查交互设计依据。这说明方法到场和方法真正改变任务判断是两个不同结果；新文字能否改善后者仍需验证。

本稿按任务成果和当前最影响结果的缺口选择专业职责。在 Core 中说明如何选择及调整工作方式；软件与可执行文本记忆在相应任务中说明专业责任、依据和验证。例子用于帮助模型辨认分支，不把例子里的产品行为提升为所有任务的规则。

## 候选正文

- [core.md](core.md)：在现有每轮意图判断之前增加长期协作者的职责定位；在意图判断之后说明如何承担所需专业职责，并用线下活动入场的跨领域例子展示选择依据。
- [software.md](software.md)：按受影响范围给出前端、后端及跨两端的开发责任；用手机筛选操作说明前端要调查使用者的真实困难并核对页面行为。现有候补功能例子继续说明业务取舍和后端实现的边界。
- [instructions.md](instructions.md)：将可执行文本的质量落到未来读者的正确行动上；用模型处理资料冲突的规则说明怎样在判断位置写清依据和下一动作。

## 静态情境核对

| 情境 | 候选文字应引导的下一步 | 容易暴露的偏差 |
| --- | --- | --- |
| 用户说“手机上筛选太费劲” | 作为前端开发者查看实际操作、项目交互与组件能力，分辨难点；按本轮授权决定是分析还是修改，并检查手机尺寸下的行为。 | 只解释组件来源，或只改外观。 |
| 用户说“给活动报名加候补”，旧代码和测试只覆盖满额拒绝 | 作为负责业务行为的开发者，查旧规则成立范围；识别补位方式等用户体验取舍；实现时核对状态、并发及失败条件。 | 把旧测试当新需求，或在用户尚未决定重要体验时自行定稿。 |
| 用户要求编写“发现资料冲突时查证”的模型规则 | 作为可执行文本编写者，明确冲突的判断位置、可区分的来源、下一动作及工具不可用时的退路。 | 只把“认真查证”写得更强烈。 |
| 用户说“让线下活动入场快一点” | 先查现场流程与可取得的记录，再据瓶颈选择现场流程、界面或服务端方法。 | 因看见报名系统就直接优化代码。 |
| 用户只要求缩短给出的句子 | 直接压缩并核对原意。 | 为简单任务启动多领域调查或冗长角色说明。 |

## 审核重点

1. 通用职责是否足够让模型在选专业方法前核对真正目标，同时不会让它在简单任务上增加无关步骤。
2. 软件正文能否使前端和后端的责任落到实际行为与证据上，并保持跨领域任务可合用多种视角。
3. 例子是否展示了不同分支，且不会让弱模型把单个案例的具体产品选择误当通用要求。
4. 新文字是否与原有判断、路线、用户取舍和验证方法一致；若出现重复，应在保持清楚的前提下合并。

本稿只作文字与情境的静态检查，没有模型回放，不能据此声称遵循度已经改善。
