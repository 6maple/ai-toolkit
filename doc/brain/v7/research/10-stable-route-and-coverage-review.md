# v7 · 稳定路由与领域读取边界复核（2026-09-24）

本文接续 [09-prompt-body-writing-review.md](09-prompt-body-writing-review.md) 的 Universal / Collaboration Root 正文候选。用户在看到两段完整中文候选后回复“可以”；这使它们成为继续设计的已接受输入。整体能力 Contract、其他 model-facing 正文与生产接入仍需按既定 Gate 分别完成。

本文是设计工作稿。当前架构结论由 [../06-current-architecture.md](../06-current-architecture.md) 拥有。这里的情境推演不等于弱模型 Replay。

## 1. 当前要解决的失败

通用 Root 可以提醒模型修正目标理解、检查材料证明范围，但它无法凭自身保证模型进入适用的专业方法。若模型还不知道需要软件设计方法，它也可能不知道自己漏了这份方法；再写一句“需要时读取 Skill”不会消除这个循环。

因此应把两个判断分开：

```text
当前消息是否落入一个范围较宽、漏读代价较高的工作领域？
→ 稳定路由从可观察的任务、产物和动作触发

进入该领域后，当前阶段真正需要哪些方法与依据？
→ 领域正文按任务条件确定必要、默认和条件性读取
```

路由不替代模型的语义判断。它降低模型在判断开始前遗漏一整类相关方法的概率；领域正文继续处理该类任务的具体差异。这个关系也不能只用文案宣称“保证”：宿主是否注入路由、目标是否存在、工具是否可用都要独立核对。

## 2. 最小路由契约

一条稳定路由至少有四项可审查的语义：

| 项目 | 必须说明什么 | 失效例子 |
|---|---|---|
| 触发条件 | 当前可观察的任务、产物、动作或续作线索 | 只写“需要专业帮助时”，模型可能不知道自己需要 |
| 下一动作 | 要立即读取哪个确定目标，或进入哪一层更具体路由 | 只给领域名称，弱模型仍需猜路径和顺序 |
| 使用范围 | 读到正文后按哪项任务应用，以及何时停止扩展 | 相关项目的旧规则被当成当前项目的规则 |
| 可达性 | 宿主已提供该 surface；目标和工具真实可用；超限时不静默丢失必要路线 | Prompt 要求的工具未暴露，或活跃工作路线被 top-k 截断 |

`importance`、相似度和普通记忆 `description` 可以帮助发现候选，不能独自承担一条保证可达的路由。正文可以修改而路径未变；一旦适用条件、目标路径或活跃状态变化，路由也必须同步维护。路由目标读取失败时，应暴露失败并选择仍有证据支持的恢复动作，不能把“已列出路由”当成“已读到 cognition”。

## 3. 各层当前职责

### 每轮直接可用的内容

Universal / Collaboration Root 的承重关系应在模型作重要语义判断前确定性可用。若只注入一条“请再读取 Root”的提示，就仍依赖模型主动完成一次可能漏掉的调用。

Global 路由面与当前 Project 路由面也要在每轮可用。它们只包含稳定入口：触发条件、明确目标、必要的使用提示。Project 身份由宿主提供；模型不应仅凭最近提到的项目猜当前 Project。

### Global 路由面

跨项目持续需要的广域方法可以进入 Global 路由。例如，涉及软件工程判断时进入软件方法；编写需要被执行的 Prompt、规则或规范时进入表达方法。这里是**路由类别的例子**，不是已经确定的 v7 路径或最终路由正文。

一条广域路由应优先依据任务表面触发，例如“修改代码、评估工程方案、排查软件行为”。更细的设计、测试、调试或可行性实验方法由软件领域内部继续分流。不同路由可以同时成立；用户既要改代码又要改 Prompt 时，不把任务强制归为单一类别。

### 当前 Project 路由面

它让当前项目的重要指导和每一项仍需跨会话继续的工作有确定入口。每项活跃工作至少提供足以辨认它的任务线索和准确正文路径。正文保存目标、当前阶段、已确认决定、进度、阻碍及下一步；路由面不复制整份状态。

同一项目可以有多个活跃工作。用户说“继续”时，模型结合当前对话、路由线索和工作正文定位具体工作；若两个工作仍都合理且会改变行动，继续核对已有上下文，必要时才请求用户指出要继续哪项。不能建立项目唯一 `currentTask`，也不能让最近更新的文件自动决定用户意图。

可访问的相关项目普通 cognition 可以通过 discovery 成为证据；相关项目的路由面和项目规则只有实际进入该项目工作时才加载。这样可借用其他项目经验，同时保持项目责任边界。

### 领域正文与主动发现

领域正文可以用三种强度说明本类任务的信息范围：

- **必要**：当前判断或阶段依赖它，缺失时无法可靠继续；
- **默认**：进入本领域通常读取，明确无关时可跳过；
- **条件性**：写明具体触发条件，成立后取得对应内容。

它们覆盖 Brain cognition、当前规范、代码、测试、运行状态、官方资料和实验等不同来源，具体取哪些由任务与领域决定。没有稳定地址的长尾历史内容仍使用主动发现。检索结果只提供候选；重要结论需要正文时继续准确读取，有限结果的未命中只报告已检查的范围。

## 4. 数量增长与失效恢复

路由面要控制噪声，但不能通过静默丢弃承担保证的路线来节省上下文。当前先保持短路由和渐进分流；一旦一个项目的活跃工作多到不能完整呈现，需有确定性索引、总数或分页状态，以及“继续某项工作”时读取完整候选范围的动作。采用哪种物理形式由实际数量、上下文成本与 Replay 决定。当前没有证据支持固定一个通用上限。

活跃工作还需要维护路由与正文之间的完整性：

```text
路由仍指向某项活跃工作
→ 对应正文存在、可读，且包含该工作的当前续作状态

工作仍承诺跨会话继续
→ 当前 Project 有可确定发现它的路线

工作已完成或经 owner 明确转为只待未来按需恢复
→ 调整或移除活跃路线，并保留仍有效的长期决定和知识
```

“暂停”本身不能机械等同于删除路线：若用户仍期待未来会话接着做，恢复入口仍有价值。当前版本还需决定更新正文与路由时，怎样避免并发或中途失败留下指向缺失正文的路线、或让应续作的工作成为不可发现的孤立正文。这里先确定结果约束；是否使用同一次事务、显式注册与投影，或可检查的修复步骤，需要依据实现成本和真实失败证据裁决。

从候选 Prompt 到真实行为至少有五个独立检查点：

```text
本轮正确的 Root / Global / Project 路由确实注入
→ 当前任务触发了适用路线
→ 路线指向的正文可读且已读取
→ 正文指导的事实来源与工具实际可用
→ 行动和验证结果符合当前目标
```

不同检查点失败，修复位置也不同。尤其是历史 tunnel 中出现过 Prompt 指向 `brain_ask_search` 而工具未暴露的真实情况；这类问题要检查宿主接线与 Tool Contract，不能归因于模型不理解路由。历史情况只证明曾发生过，不能断言当前仍存在。

## 5. 成对情境自检与下一步验证

| 改变的条件 | 正确的区别 | 主要检查点 |
|---|---|---|
| 用户提出模糊新功能 / 明确局部修改 | 前者恢复既有决定并形成可纠正的目标理解；后者在适用读取与检查后直接完成 | 路由不漏、也不过量阻塞 |
| 旧规范与旧测试一致 / 当前运行结果冲突 | 两者都要区分旧意图和当前事实；冲突时追加当前观测并修正理解 | 领域覆盖与来源边界 |
| 当前项目一项 / 多项活跃工作 | 多项时不能按最近更新时间单选；结合对话和路线线索定位 | Project 路由完整性 |
| 相关项目有普通经验 / 用户实际转入相关项目工作 | 前者按需发现普通 cognition；后者加载该项目自己的路由与规则 | scope 与适用性 |
| 搜索没有命中 / 搜索工具根本不可用 | 前者检查范围、分页、索引与必要正文；后者检查宿主能力和接线 | 检索与运行时责任 |
| 必要路线数量少 / 数量超过展示预算 | 后者仍保留可确定访问的完整索引及状态，不静默 top-k | 容量与恢复语义 |

下一步真实 Replay 应使用选定的较弱模型和真实工具表，记录它看到的每轮注入、工具选择、正文读取、停止时机和用户负担。每组改变一个条件，必要时移除 Root、路由或领域覆盖其中一层做对照，才能判断失效落在哪层。当前表格是设计自检，不能代替这项验证。

## 6. 路由执行说明的完整中文候选

下面是一段拟随 Global / 当前 Project 路由面一同提供给模型的**通用执行说明**。它只定义模型怎样使用本轮已注入的路由；各条路由的条件和目标仍由其 canonical owner 维护。工具名按当前 Brain 的实际接口写出，v7 能力 Contract 若调整接口，必须重新审查这段文字。

```text
# 读取适用的认知

本轮提供的 Global Core 和当前 Project Core 是稳定读取入口。结合当前任务逐条检查其中的触发条件；一项任务可以同时触发多条。条件成立时，先按所列准确路径使用 brain_cat 读取正文，再应用正文中的决定、事实、方法或续作状态。若读取结果给出 next_offset，继续从该位置读取，直到取得当前所需的完整内容。

Core 中的短说明帮助找到正文；正文的来源、适用条件和当前状态决定它能怎样用于这次任务。读取目标失败或工具不可用时，检查实际可用的路径与工具，说明尚未取得哪项重要内容，并在可用来源中继续调查。无法取得会改变当前行动的必要内容时，先处理这个缺口。

没有稳定路径、但当前判断需要过去的认识时，使用本轮实际提供的 Brain 发现工具寻找候选；候选需要支持重要判断时，继续读取相应正文。当前 Project 的路由只适用于当前项目；相关项目中的普通认识可按需发现。准备读取、修改或分析相关项目文件，或者要根据该项目当前状态作决定时，先按本轮给出的准确路径读取并遵循该项目自己的入口。
```

这段文字依赖宿主已准确绑定当前 Project，并已提供 Global / Project Core 和 `brain_cat`。它不能独自保证模型实际读取；注入、可达性与工具注册需要在 Harness / Tool 层独立验证。`next_offset` 属于当前工具返回协议，属于这里需要就近写清的执行细节。

### 用当前配置校准“准确路径”

当前工作区的真实路由例子包括：任意任务从 `@global/core.md` 进入 `@global/memories/skill/ai-think/core.md`；继续 Brain Base / v7 设计时，`@project/core.md` 指向 `@project/memories/intention/brain-base-cognitive-harness-redesign.md`。这两个具体 body 已可由当前 `brain_cat` 读取。它们说明动态路由条目怎样给出准确目标，不把 ai-think 的路径固化为所有 Brain 用户的内置路由。

当前代码提供了可行性依据：[runtime/bootstrap.ts](../../../../code/brain/src/runtime/bootstrap.ts) 在运行时准备 Global / Project 两个 Core；[application/anchor-renderer.ts](../../../../code/brain/src/application/anchor-renderer.ts) 能在上下文中呈现两个 Core、相关项目边界和 `brain_cat` 读取引导；[integration/public-tools.ts](../../../../code/brain/src/integration/public-tools.ts) 暴露相应读取工具。这说明现有实现具备若干必要部件，不证明 v7 候选已经按每轮、完整路由与目标可达性要求接线。具体实现仍需独立设计和验证。

### 当前候选仍需处理的矛盾

第二段说“无法取得必要内容时，先处理缺口”，但现实中工具未暴露、权限不足或目标暂时损坏时，模型可能无法自行补齐。此时要依据当前任务决定：可用的其他来源能否提供足够依据；能则继续，不能则报告具体缺口与影响。不能为了让 Prompt 看起来闭合，写成“总能恢复”。

路由条目若很多，模型逐条检查也可能漏掉中部条目。是否需要 deterministic grouping、分层目录或宿主预筛，取决于真实规模和回放结果；任何预筛都必须保留承担保证的路线的可达性。这里尚未选择物理方案。

## 7. 首次工具回放的评价基线

先做一个只检查**可达性与准确读取**的小实验，再谈整体行为改善：

- 问题：较弱模型在当前 Codex CLI 与 Brain MCP 工具表下，面对“继续 Brain v7 路由设计”，能否按当前 Project route 调用 `brain_cat` 读取 `@project/memories/intention/brain-base-cognitive-harness-redesign.md`？
- 样本：当前项目、只读任务、完整路由执行说明和准确 Project route；不要求修改文档或生产代码。
- Pass：日志显示工具真实暴露，模型调用正确路径并取得正文，回答中保留“尚无弱模型 Replay、生产 Gate 尚未完成”等仍有效条件。
- Partial：能读到正文，但工具表、注入来源或回答依据无法区分；只支持“在此环境可读”，不支持 Prompt 因果效应。
- Fail：工具缺失、路径错误、未读取却声称已读，或把候选误报为获批的整体 production Prompt。
- 停止：完成这一轮后不通过重复运行凑成功；将观察到的失败分配给 Prompt、route、Tool 或 host 条件，再设计下一实验。

CLI 可能加载已有 `AGENTS.md`、用户配置与宿主指令，因此即使 Pass，也只能证明这一组合环境下的表现。要判断候选 Root / route 的因果收益，后续仍需控制组、多个场景和同一工具条件下的重复样本。

### 本次尝试的实际结果

1. 使用 `gpt-6-luna`、当前项目、只读沙箱和 Codex CLI 启动一次回放。CLI 配置列出了 Brain MCP，但模型请求持续超时；运行约两分钟后停止，JSONL 事件文件为 0 字节，没有模型消息或 `brain_cat` 调用。沙箱外重跑起初被自动审批拒绝，理由是可能向外部模型服务发送工作区、配置或 Brain 上下文。用户获知风险后明确允许**本次只读回放**，于是按原命令重试；服务端最终返回当前 CLI ChatGPT 账户不支持 `gpt-6-luna`。这两次运行都没有可评价的模型行为。
2. 为完成同一问题，改用 CLI 可接受的较旧 `gpt-5.5`，保持任务、只读范围和路由文字一致。日志记录到模型先调用 `brain.brain_cat`，准确传入 `@project/memories/intention/brain-base-cognitive-harness-redesign.md`；调用返回 `codex-invocation-context-unavailable`。模型尝试备用 `codex_apps.lpc.brain_cat`，同一路径返回 `not-found`；随后尝试读取 `@project/core.md`，只得到路径名。模型继续尝试发现，但运行中的 Windows 只读 sandbox 命令失败，随后子进程自身的自动审批拒绝了其沙箱升级请求；此时停止回放，没有得到完整最终回答。对**选中正确路线与路径**有一次直接观察；对**成功读到正文、正确应用和完成任务**仍无证据。

当前 [Codex plugin 的读取绑定](../../../../code/brain-codex-plugin/src/invocation-binding.ts) 在缺少 session binding 时会返回该错误；[UserPromptSubmit hook](../../../../code/brain-codex-plugin/src/user-prompt-submit.ts) 负责写入 binding。CLI 启动时同时警告有 hook manifest 未被识别，这为“hook 没有正确建立绑定”提供了合理线索，但没有取得完整的 hook 执行证据，原因仍待核对。这个失效位于 Host / Tool 可达性边界，不能靠修改 Root 文案解释为模型没有选对路径。备用 `codex_apps` 入口为何读取不到同一项目正文也未确认。

此次用户授权只覆盖本次只读外部回放；子进程沙箱升级仍被其自动审批拒绝。当前停止模型实验，不通过其他命令绕过拒绝。后续评估应先让回放环境真实提供可用的 Brain 读取接口，再沿既定用例比较 Prompt 行为。
