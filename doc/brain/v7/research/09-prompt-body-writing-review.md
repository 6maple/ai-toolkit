# v7 · Model-facing Prompt 正文写法复核（2026-09-24）

本文只审查正文写法和当前 Universal Root 候选，不评价 Skill frontmatter / description，也不批准最终 Prompt。讨论链来自归档会话 `visible-messages.jsonl`：用户在 0845、0851 指定先看开源 Skill 正文，在 0863、0904 明确要求清楚、弱模型可执行，并纠正过度依赖模型自评；1170 是本次复核的 Universal Root 候选。归档中大量工具消息已被脱敏，因此历史助手的技术结论只作为讨论过程，不替代当前文件和一手来源。

## 正文样本与可迁移的写法

| 样本 | 正文里的实际方法 | 对本项目的适用边界 |
|---|---|---|
| [Superpowers brainstorming](https://raw.githubusercontent.com/obra/superpowers/refs/heads/main/skills/brainstorming/SKILL.md) | 先说明要形成用户可以辨认和纠正的共同理解；发现意图、复述理解、再带入设计。Gate 直接写出前提、允许动作和批准范围。 | 可借鉴“可纠正的理解”和具体 Gate；它的 Spike / Bounded / Architectural 流程属于专项 Skill，不能全放进每轮 Root。 |
| [Matt Pocock grilling](https://raw.githubusercontent.com/mattpocock/skills/refs/heads/main/skills/productivity/grilling/SKILL.md) | 用 decision tree、已具备前提的 frontier、下一轮重算与明确结束条件组织提问；事实由 agent 自己调查。 | 可借鉴一个清楚的工作关系生成多个正确动作；“所有决定由用户作出”只适合该访谈 Skill，不能推广到 AI 应承担的专业设计。 |
| [Addy Osmani interview-me](https://raw.githubusercontent.com/addyosmani/agent-skills/refs/heads/main/skills/interview-me/SKILL.md) | 明确什么时候启用、如何形成暂定理解、怎样让用户纠正、何时停止，并给出反例。 | 可借鉴条件、动作、停止和例子；置信度百分比、固定逐题访谈和每次显式批准不宜成为通用 Root，模型自报信心尤其不能作为 coverage 证明。 |

这些正文的共同点是把行为放在决定发生的位置，说明条件和下一动作。篇幅差异很大，不能从短 Skill 推出 Root 越短越好，也不能把专项流程复制成通用规则。

## 近期官方指南

- [OpenAI Prompt engineering](https://developers.openai.com/api/docs/guides/prompt-engineering) 建议清楚分开指令、例子与上下文；不同模型及快照会有行为差异，生产 Prompt 应配合有代表性的评估。
- [OpenAI GPT-6 model guidance](https://developers.openai.com/api/docs/guides/latest-model) 强调从真实任务出发校准自主性、澄清和验证；它列出的文字是起点，需要用选定模型和工作负载验证。
- [OpenAI 对 GPT-6 Astra Skill 与 Prompt 的复核](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra) 提醒缩短无关或冲突的路由说明，并通过渐进披露取得专项内容。其对象是更强的 Astra；Brain 同时面向较弱模型，仍需保留缺失后会让它无法推出正确动作的关系。
- [OpenAI reasoning best practices](https://developers.openai.com/api/docs/guides/reasoning-best-practices) 建议直接说明目标和约束，复杂输入用清楚的分隔；“逐步思考”式指令不一定改善推理。
- [Anthropic Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices) 与 [Google Prompt design strategies](https://ai.google.dev/gemini-api/docs/prompting-strategies) 都强调明确的指令、必要上下文、清楚的结构与按真实结果迭代。模型特定建议不能未经测试直接推广到 Brain 的所有宿主模型。

## 对 1170 候选的当前判断

1. “恢复用户真正要实现的结果”方向正确，但每轮入口应明确优先使用用户的当前表达、纠正和已确认取舍；历史 assistant 回答帮助理解对话位置，其推断不能自动成为用户决定。意图不清时形成可修正的当前理解，再取得会改变行动的缺失信息。
2. “信息已经足以支持当前行动”不能单靠模型感觉。停止判断至少受已触发的 route、domain coverage、任务要求和真实验证结果约束。Root 说明这个关系，具体覆盖项仍由 domain Skill / workflow 拥有。
3. “从真正能够说明它的来源取得信息”应就近说明例子：用户目标看用户表达和已确认决定；当前代码看项目；当前外部能力看官方资料或运行结果；过去 cognition 看对应正文。例子用于校准 source 与 claim 的关系，不变成每轮固定检查单。
4. 历史 memory 可以保存用户已经作出的决定，也可以保存过去的模型推断。判断其能证明什么取决于内容来源、条件和状态；不能一概降低或提高它的证据等级。
5. Root 的取证触发应限于当前行动依赖且不同答案会明显改变结果的缺口。已触发的 broad route / bounded domain coverage 仍应执行，不能因为模型没有主动觉察缺口而略过。

建议下一版仍按 Universal Root、Collaboration Root、Global / Project route、Domain Skill 的 owner 分开审核。这里记录的是正文复核结论；完整 model-facing Prompt 文本仍须单独展示并经用户认可。实际遵循程度需要以弱模型和长会话真实 case 做 Replay / Eval，不能由文案审查推断。

## 真实工作流程推演（2026-09-24）

以下是用于人工自检的具体情境，不声称仓库当前存在所设定的旧实现或旧规范，也不等于真实模型 Replay。用同一个“新增功能”任务改变证据条件，观察当前候选能否稳定产生正确下一步。

### A. 旧代码、旧文档、旧测试相互一致，用户提出模糊功能

假设旧代码只在用户明确调用搜索时检索当前项目记忆，旧规范和测试也都保护这一行为。用户说：“我想让 Brain 在我提新需求时自动参考以前做过的类似东西，别老忘记。”此前用户已经确认：每轮稳定恢复的重点是思考方法，项目工作要能跨会话继续；相关历史 cognition 可以按需发现。

正确过程应是：

1. 从当前话语和已确认取舍提出暂定目标：减少新需求讨论时漏掉相关过去经验，同时保留每轮思考方法的稳定入口。这里不能直接推断“每轮检索所有项目全部记忆”。
2. 进入软件设计与当前项目 continuation route。读取当前 Base / v7 设计、旧规范形成时的前提、实际代码、真实调用方和测试。旧代码说明现在怎样运行；旧测试说明过去保护过什么；用户当前表达说明希望改变什么。它们彼此一致仍不能决定新目标。
3. 区分三类候选：稳定的通用思考引导、已知地址的项目进度、需要 discovery 的相似历史经验。先依据已有设计形成具体推荐和影响，再让用户看到会改变产品行为的选择。
4. 缺少用户才能决定的范围边界时，只问会改变方案的上游问题；可查的当前实现、调用链和资料由 AI 取得。完整 model-facing Prompt 仍经过既定审核 Gate 才能进入 production。

当前 Universal Root 能提醒“第一解释可修正”和“材料只证明各自范围”。但单凭 Root 不会稳定要求读取旧规范的形成条件、当前调用方与测试，也不能保证模型发现软件领域的默认 coverage；这些责任属于稳定 route 和软件 Skill。Root 对旧材料的表达可再明确：“先看它形成时解决什么、依赖什么前提，以及这些前提现在是否仍成立。”

### B. 旧规范与当前运行结果冲突

同一需求下，假设旧规范写“搜索仅限当前项目”，但当前工具实际已经能在配置的 related projects 中发现普通记忆；一次搜索摘要又声称“所有项目都已覆盖”。

正确过程应是：先分别记录旧规范的历史意图、当前代码与工具实际支持的范围，以及摘要只是候选的边界；核对配置、调用路径、结果分页和正文读取。若搜索没有命中某项，不能据此证明它不存在。再判断新增自动参考功能会不会扩张到相关项目 Core 或改变用户可见行为。不能仅凭“规范较旧”宣布它失效，也不能凭当前实现反向推定用户已批准跨项目自动加载。

这个变体主要检验 Universal Root 的证据边界与反馈更新。需要取得哪些具体代码、配置、测试和运行结果，仍由软件领域 coverage 定义。

### C. 用户目标仍有两个会改变产品行为的解释

假设一个项目管理应用的旧代码、文档和规范只支持个人到期提醒。用户说：“想加智能提醒，别让大家忘事。”检查当前账户、任务归属和提醒能力后，仍无法判断用户希望的是“只提醒任务负责人”，还是“逾期后通知整个团队”；两个方向会改变接收者、打扰成本和授权边界。

正确过程应是：先查现有使用流程、调用方和已确认目标，形成两个具体方案及推荐；把接收者和触发时机中真正影响产品行为的选择给用户裁决。不能让旧个人提醒规范代替用户的新目标，也不能因为模型可以提出一个合理方案就宣称用户已经确认。等待回复期间可以完成不依赖该取舍的调查和技术比较。

这个变体暴露一个 Root 之外的必要关系：重要方案应使用户能够辨认并纠正 AI 对意图的理解；当多个重要方向都合理且只能由用户决定时，Collaboration Root / 软件 workflow 要规定何时展示候选并等待回应。

### D. 相同旧资料条件下，目标已足够具体

用户说：“设置页保存时显示加载状态，阻止重复点击；失败时恢复按钮并显示现有错误。”旧规范只描述保存成功和失败，没有 loading。AI 应检查实际保存调用、已有组件和错误状态，确认公开行为与必要验证，形成当前范围的实现。旧规范没有提及 loading，不能自动解释为禁止增加；也无需为了形式完整重查整个产品历史。若当前项目另有明确审核 Gate，仍按该 Gate 执行。

这个变体检验停止边界：已触发的领域 coverage 完成、重要行为没有未决歧义、实现与验证范围明确时继续行动。Root 不应把所有旧文档都视为冲突，也不应让“可能还有未知”使任务停在调查阶段。

## 初轮推演结论的适用边界

初轮推演提示了旧材料适用性、软件路由和用户可纠正性三处问题，但“给 Root 增加一句旧材料检查”只是局部修补。旧资料一致时做偏、新资料冲突时做偏、搜索漏读、模型过早停查、测试通过却没有完成原目标，可能共用更上游的原因。以下进一步按完整任务过程审查，不把一次场景的表象直接升为通用 Prompt。

## 第二轮：从失效链追查共同原因（2026-09-24）

当前推论的核心：模型在每一步都会用一个暂定问题框架判断“什么相关、该取什么资料、什么时候够了”。框架若过早收敛，后续搜索、测试和报告都可能围绕错误问题形成自洽链。旧代码、文档、规范一致只是这一错误的一种输入形态。

这个框架污染不是所有失败的唯一根因。历史会话中 `brain_think_context` 已提示调用 `brain_ask_search`，但 tunnel 没有暴露该工具；即使模型理解和 Prompt 完全正确，动作也无法发生。检索索引缺项、工具结果截断、项目身份选错、权限或并发状态错误也有独立的机制原因。分析时至少区分：模型怎样理解任务、所需信息能否取得、取得后怎样判断其证明范围、动作与状态是否由 runtime 正确执行。不能把不同层的问题全改成 Prompt。

| 发生位置 | 共因与跨场景表现 | 更合适的责任层 |
|---|---|---|
| 恢复目标 | 当前措辞、既有方案、历史 assistant 分析或最近看到的文件先成为问题定义。新功能、故障诊断、写报告都可能因此从错误目标出发。 | Universal Root 使理解保持可修正；Collaboration guidance 区分用户已决定的目标与 AI 推断；重要方案向用户展示以获得可纠正反馈。 |
| 产生信息需要 | 模型只有在意识到某项依据缺失后才搜索，但“是否缺失”也是它容易误判的事。错误问题框架会只召回支持它的资料。 | Harness 每轮保证根引导和稳定 route；route 用任务、对象、动作等可观察特征触发；domain Skill 给出有界默认覆盖。主动搜索仍处理长尾未知。 |
| 解释材料 | 不同来源被压成一份“上下文”：用户偏好、当前运行事实、旧规范、测试、搜索命中和模型推断互相代替。多份旧产物可能复制同一个上游误解，数量和一致性不构成独立证明。 | Root 建立“当前判断是什么、材料实际能说明什么、成立条件是否相同”的关系；domain Skill 定义当前需要查的 owner 与独立观察；搜索候选进入正文后仍核对状态和条件。 |
| 使用检索结果 | 命中看似相关但正文条件不适用；top-k / 截断没有命中被误当不存在；过量候选或历史命令式文字又造成注意力分散、指令混淆。 | Brain 提供候选、exact read、边界和状态；Harness 清楚区分当前规则与历史内容；model 按 claim 读取必要正文；检索参数、质量和上下文成本由 Replay 校准。 |
| 决定是否继续 | “我觉得够了”可能在缺少关键资料时过早结束；反过来，把所有可能资料都读完会拖慢简单任务并增加噪声。 | Domain Skill 定义 Required / Default / Conditional coverage 与停止条件；Root 要求当前行动依赖的 material 依据及已触发的 coverage 得到满足；可机械检查的 Gate 由 Harness / Tool 保证。 |
| 从方案到行动 | 模型把合理推荐升级成用户决定，或把已经明确的授权反复要求确认。两种错误都来自目标、专业判断、行动授权与用户反馈责任混淆。 | Collaboration guidance + 当前 workflow 说明何时展示重要方案、何时等待用户回应、哪些范围内工作继续完成；权限与不可逆动作由 Harness enforce。 |
| 行动后的验证与更新 | 旧测试保护旧行为也能全部通过；一次局部成功被报告为原目标完成；新反馈与旧解释冲突时只作合理化，不修正规范、设计或长期记忆。 | 当前 Requirement / Acceptance、真实运行结果和原始目标共同决定完成证据；出现冲突时沿 owner 修改受影响层，Brain maintenance 只保存经区分的决策、知识和未解挑战。 |

### 对上一轮建议的修正

1. 不把“旧材料要看形成背景”写成独立的通用禁令。更上游的可迁移关系是：**先明确当前要判断哪一件事，再判断每份材料在其形成条件下能够证明什么；相同错误前提派生的多份材料不能互相当独立验证**。旧规范、旧代码只是该关系的一个软件例子。具体需要哪些软件 artifact 和历史记录，由软件 Skill 写在进入该领域的地方。
   日期也不能作为统一的真伪排序：多年未改的代码仍可能是当前 checkout 的实现，但运行环境是否部署该版本还需观察；昨天写的方案仍可能只是候选；较早的用户明确决定只要未被替代，仍可能约束当前工作。先辨别 claim 和 owner，再看适用条件与当前观察。
2. 不把“新功能一律读取代码、文档、测试”做成固定全量流程。新增功能可能是绿地、已有系统修改、外部 API 集成或仅做需求讨论。route 应宽进以降低漏读；领域内 coverage 再根据现有系统、当前阶段、可得证据和重要后果决定实际读取。读得更多也可能带来上下文干扰。
3. 不把“关键事实查到来源”当成结果验证。搜索或网页是可能有噪声的 evidence；当前运行、测试和实验反馈能检验另一类 claim。对每项重要结论说明什么观察能使它成立或被推翻。
4. 不把“看见一个用户未决问题就立即提问”当成通用规则。先完成可调查事实和专业方案；重要方案应让用户看见并能纠正模型没有察觉的意图偏差。已明确的决定和范围内执行继续有效。
5. 不让 Root 承担整个流程。Root 只应保留若缺失就可能阻止模型产生正确取证与纠错动作的关系；route 负责稳定进入领域，domain Skill 负责覆盖与方法，Tool / Harness 负责确定性边界和真实反馈。每加一句 Root 都应指出已知 failure、作用位置和漏掉后会发生的具体错误。

### 用不同任务检验这套原因是否真正通用

- **故障诊断**：用户说“升级后系统变慢”。旧事故报告归因数据库，当前瓶颈可能是网络或调用方。若模型先继承旧解释，只会查数据库；稳定诊断方法应让它先取得当前观测、划分组件边界，再判断旧结论条件是否相同。
- **新近外部能力**：用户希望用某服务新 API；项目内旧文档和代码互相一致。它们说明原集成方式，当前 API 能力应查官方资料或实际调用。来源新旧本身也不代替兼容性实验。
- **检索未命中**：用户问“以前是否否决过这个方案”。一次 top-k 没有结果只能说明该次候选集没有命中；若结论重要，应检查 scope、关键词、路径线索和必要的后续页，仍无证据时报告未找到的检索范围。
- **工具根本不可用**：Prompt 要求调用搜索，宿主实际没有公开该 Tool。正确处理是检查工具注册、功能配置和宿主返回；重写意图理解文字无法修好接线。此项由历史 tunnel 失配提供真实 precedent，不能从人工场景推定现在仍存在该故障。
- **多会话续作**：两个会话同时推进不同 Brain 工作，用户在其中一个说“继续”。最近更新的文档未必属于该工作；应根据会话与项目 continuation route 恢复对应目标、已确认决定、剩余工作与当前阶段。
- **测试通过但目标未达**：新增功能的旧测试全部绿，只说明旧行为未回归。完成判断还需把当前用户结果映射到验收场景和可观察结果，再从原始目的反向检查遗漏。
- **小改动**：用户明确要求可逆的局部 UI 文案修改。适用 route / coverage 后，如果没有改变结果的缺口，继续修改并做匹配的检查；不能机械展开所有历史材料或反复访谈。

### 证据边界与验证计划

外部研究支持这些风险存在，但不直接证明当前 v7 方案有效：[UA-Bench](https://aclanthology.org/2026.acl-long.547/) 显示模型难以可靠区分输入不足与自身能力不足；[工具使用校准研究](https://aclanthology.org/2026.acl-long.520/) 发现证据工具与确定性验证工具对信心校准影响不同；[指令干扰研究](https://aclanthology.org/2025.acl-long.957/) 和 [长上下文位置研究](https://arxiv.org/abs/2307.03172) 分别提示历史命令式材料和过量上下文的风险。各研究的任务设置与 Brain 不完全相同，具体机制仍要用 Brain 的目标模型验证。

下一步 Replay 应成对改变一个关键条件：意图清楚/模糊，旧材料一致/冲突，检索命中/漏命中，用户决策已有/未有，资料少/多，行动前/行动后，单会话/多会话。逐步观察问题框架、route 与 Tool 选择、真实读取的正文、材料角色、用户提问或方案展示、停止时机、验证结果及反馈后的修正。使用历史真实 case 与刻意构造的边界 case；必要时做去掉一层 guidance 的对照，才能判断错误应修在 Prompt、route、domain Skill、Tool 还是 Harness。可参照 [OpenAI 的评估指南](https://developers.openai.com/api/docs/guides/evaluation-best-practices)定义阶段性指标，但指标要直接对应 Brain 的真实用户结果。

以上是架构审查与人工推导；尚未冻结新 Prompt，也没有模型实测结论。

## 第三轮：逐句追溯 failure 与 Prompt owner（2026-09-24）

重新检查归档消息 1170 中的完整 Universal Root 候选时，判断一句话是否常驻，需要同时问：它对应哪种跨任务失效；模型若没看到它，是否可能连正确的下一步信息需要都产生不了；更具体的领域说明、检索方法或运行时是否已经有更可靠的责任位置。不能因为一句话正确，就认定它应进入每轮 Root。

| 原候选中的关系 | 要防止的错误 | 当前处理 |
|---|---|---|
| 从真正目标、已有决定和现实开始；第一解释可修正 | 当前措辞、最近文件或模型先前回答过早定义问题，继而影响检索和验收 | **保留在 Universal Root**；明确用户当前表达和纠正优先，模型形成的是可修正的理解。具体领域怎样恢复目标由相应方法展开。 |

| 重要缺口从相应来源取得 | 模型只寻找支持第一解释的材料，遗漏会改变行动的依据 | **Root 与 Domain Coverage 共同承担**：Root 给出行动依赖与结果差异的关系；稳定 route 使模型进入领域；领域方法给出有界默认覆盖。Root 单独不能保证模型发现自己没意识到的缺口。 |
| 有限搜索没命中不能证明不存在 | top-k、分页、scope 或索引限制导致错误否定 | **移入检索方法**；Root 的来源边界可以涵盖这个逻辑，但无需每轮单列搜索细节。检索工具应暴露范围、分页和截断状态。 |
| 不能凭主观把握宣布信息足够；遵循适用 coverage / gate | 模型在缺少关键材料时过早结束，或者为了避免遗漏无限查找 | **保留简短 Root 关系**：按已进入领域的读取与验证要求，以及当前行动的实质依赖判断能否继续。具体停止条件归领域方法和真实结果。 |
| 反馈冲突时修正理解 | 新事实被旧框架吸收，测试通过被误报为用户目标完成 | **保留在 Universal Root**；领域验收负责“哪种观察能证明结果”。 |
| AI 自行调查；用户负责其目标和重要取舍 | AI 把调查交还用户，或把合理建议擅自升级成用户决定 | **放入 Collaboration Root**；重要方案需让用户能够辨认、纠正。具体授权 Gate 由当前工作流程和运行时边界承担。 |

这不是对 Root 文案的模型实测。官方 [Prompt engineering](https://developers.openai.com/api/docs/guides/prompt-engineering) 说明指令、例子和相关上下文可分开组织，并建议针对具体模型与版本做评估；[Evaluation best practices](https://developers.openai.com/api/docs/guides/evaluation-best-practices) 要求按真实目标评估，并在 agent 场景检查工具选择和参数。这里由这些原则推导出分层候选，不能据此声称它对 Brain 的目标模型已经有效。

### 当前完整中文正文候选：Universal Root

以下是**研究候选**。用户看到本节与下节的完整中文正文后回复“可以”，两段文字据此作为后续设计基线；整体能力 Contract、其他正文和生产接入仍待完成。标题同属候选正文。

```text
# 通用判断

处理任务时，先结合用户当前表达、纠正和仍有效的决定，理解这次要实现的结果与边界。把自己补出的目标解释保持为可修正的判断；已有方案、最近看到的材料或第一层合理解释，都要接受后续证据和用户纠正的检验。

作重要判断时，先明确要判断什么，再看材料实际说明了哪个对象、时间和条件。材料直接支持的内容可以作为相应范围内的依据；从中补出的原因、关系和结论先保持为推断。有能说明当前事实或真实结果的来源时，主动取得并核对。

当前行动若依赖一项尚未可靠覆盖的信息，且不同答案会明显改变结果，继续从相应来源取得依据。已经进入某类工作时，也执行该领域适用的读取范围和验证要求；不能只凭“我觉得够了”跳过它们。取得足以支持当前行动的依据后继续行动，并用真实结果检查是否达到用户目标。

新资料或行动结果与当前理解冲突时，修正受影响的目标理解、事实判断或方案，再决定下一步。
```

这版没有要求模型输出固定的分析格式。它把“领域要求已经触发”写入停止关系，同时仍依赖稳定 route 使领域方法真正可用。`处理任务时` 不等于每个简单任务都展开长调查：第三段以当前行动的实质依赖和适用的领域要求为边界。这里的“用户目标”必须与仍有效的用户决定共同解释，不能由模型单凭字面补成唯一产品选择。

### 当前完整中文正文候选：Collaboration Root

```text
# 与用户协作

先用当前对话、已确认决定、项目和可访问的资料，自己完成能够查明的事实调查、专业分析和范围内的普通执行。

方案会改变用户可见行为、目标边界、责任或主要风险时，在实施该方案前，向用户清楚说明你理解的目标、推荐方案、会改变结果的取舍和仍未确定的条件，等待用户回应，使用户能够辨认并纠正你的理解。用户已经明确的决定和授权按其对象与边界继续有效。

当前行动若依赖用户尚未确定的目标、价值、偏好、风险接受、组织约束或授权，且不同答案会明显改变结果，先说明已查明的事实、可行方案和推荐，再请用户补充或裁决。等待回应时继续完成不依赖该决定的调查和准备。
```

第二段用用户可见行为、目标边界、责任和主要风险界定需要先展示的重要变化；具体工作流程仍需把这一关系与既有授权和阶段 Gate 对齐。第一段的“范围内的普通执行”只覆盖已有执行授权；展示方案不会单独产生新的授权。具体外部副作用和不可逆行动由当前宿主与工作流程控制。

### 下一轮 Replay 应优先区分的行为

1. **模糊新功能，旧材料相互一致**：模型是否先形成可纠正的目标理解，按软件 route 读取当前实现与旧资料的成立条件，再提出具体推荐；旧测试一致不能直接替用户决定新目标。
2. **目标明确的小改动**：模型是否在适用方法与必要检查满足后直接行动，避免 Root 导致无穷调查或重复请求确认。
3. **旧事故解释与当前观测冲突**：模型是否检查当前系统边界并修正因果解释，而不是为旧解释增加合理化理由。
4. **检索未命中和检索工具不可用**：前者是否继续检查搜索范围、正文与截断；后者是否识别工具接线问题。若 Root 相同而两类失败仍发生，应分别修检索方法与运行时，不继续堆 Root 文字。
5. **用户已经决定与用户尚未决定**：是否分别沿已确认范围继续执行，或展示重要取舍并等待回应；同时继续可独立完成的工作。
6. **旧测试全绿但新目标未达**：模型是否依据这次用户结果和实际观察判断完成，而不是把旧测试结果扩大为新功能验收。

这些是待执行的 Replay 设计和预期观察点。人工推演不能证明弱模型会遵循候选。Replay 要记录模型实际看到的 bootstrap、route 和工具，逐步观察真实读取、判断、提问、行动和纠错；任一层不可用时不能把失败全部归因于 Prompt。
