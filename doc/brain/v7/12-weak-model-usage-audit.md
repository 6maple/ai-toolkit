# 12 · 以较弱模型为使用者的 Brain 自检（待审核）

本文检查 [默认记忆包](10-default-memory-pack-design.md)、[模型可见文字](08-model-facing-and-memory-text-draft.md) 和 [runtime／CLI 复核](11-runtime-and-cli-contract-review.md) 在较弱模型手中是否容易执行。这里的“较弱”指更可能漏掉隐含条件、少做一次工具调用、把候选当结论、过早认为资料足够的模型行为；并非对某个具体模型的实测结论。用户已经决定由自己做模型人工验证，本文只做代码核对和场景推演。

## 1. 结论及证据边界

现在不能声称“较弱模型能有较好的效果”，但也不应假定它做不到“看到明确路径后立即读取”。这是可以采用的基本执行能力；Global Core 的一行准确入口和 `brain_cat` 足以形成清楚的下一动作。需要重点审查的是读取正文后如何判断哪些历史认知还可能相关、何时搜索、怎样筛选有限候选，以及工具是否真的可用。当前语义搜索的文字又把“已配置”近似当成“可用”，这些判断和能力边界才是更直接的风险。

这些风险不证明方案无效；它们说明 11 中“路径和线索仍不足时才搜索”太依赖模型先发现自己的信息缺口。更适合较弱模型的候选是：**准确路径直接读；任务依赖已有项目或历史状态、但没有指向当前事项的具体记忆路径时，做一次有界发现；只依赖本轮材料的任务跳过。** 这里要区分通用方法路径与当前事项的决定／续作路径；读到通用方法不代表已经找到项目历史。

OpenAI 官方资料明确区分不同模型的指令需求，并建议针对实际任务建立评估；Agent 的工具选择、参数准确性和最终结果应分别观察。这支持把 Brain 的链路分步检查，不证明下述具体规则已经改善某个弱模型。[Prompt engineering](https://developers.openai.com/api/docs/guides/prompt-engineering) · [Evaluation best practices](https://developers.openai.com/api/docs/guides/evaluation-best-practices)

## 2. 沿模型实际行动链检查

| 模型需要做的动作 | 当前支持 | 较弱模型的主要失效 | 当前判断 |
|---|---|---|---|
| 建立本轮 Brain 上下文 | Codex／Claude／DSH hook 自动注入；普通 MCP 由模型按 server instruction 调 `brain_think`。 | 显式模式可能漏调；hook 接线失败时模型未必知道缺了什么。 | 自动 hook 降低一次模型调用风险；须核对真实宿主接线，不能只审正文。 |
| 找到并读取通用方法 | Global Core 含一行 `brain-ai/core.md` 入口；renderer 提醒按路径读取。 | 路径损坏、工具不可用或正文未读完整会使方法缺席。 | 对明确的“立即读取准确路径”，按模型能执行来设计；静态检查核对路径和工具，人工使用再观察实际遵循。 |
| 进入软件或可执行文本方法 | 包入口用任务类型指向 `software.md`／`instructions.md`。 | 兼具代码与 Prompt 的任务可能只读一个，或者读完未应用。 | 重点是多条件可同时成立、正文与任务对应，不把“多一次调用”本身当成失败。 |
| 发现未列出的历史认知 | Core、被动候选和 `brain_glob`／`brain_grep`；启用时有 `brain_ask_search`。 | “我已经有足够线索吗？”和“有没有未知的重要记忆？”都是不可靠的停止判断。 | 不以主观信息充足感作为唯一搜索开关；改用可观察的任务触发。 |
| 选择并读取搜索结果 | 语义搜索按相似度返回最多 10 条描述，结果需再 `brain_cat`。 | 把高排名描述当事实；只读第一条；漏读 questioned 状态；看不到目标就断言不存在。 | 返回结果和 Prompt 都要明确候选性质、范围与后续准确读取。 |
| 判断何时保存认知 | 当前 runtime 给出角色与保存协议；目标是包或用户记忆提供保存方法，工具描述保留接口契约。 | “以后仍需使用”过于抽象，容易把临时输出保存成长期事实，或漏掉已确认决定和续作状态。 | 包内用用户确认、续作需要、经验证的可复用认识、具体反证作为检查信号；先理解指向并查证，再判断价值、查同一认知并决定是否维护。 |
| 形成行动和验证 | 包正文区分旧资料、新目标、用户决定与专业执行。 | 旧代码、规范、测试表面一致时过早收敛；虽读到方法却未应用到目标和验证。 | 不能以工具调用成功代替最终行为检查。 |

此外，当前 `anchor-restore.ts` 的被动候选最多 10 条、渲染预算为 8192 UTF-8 字节。未出现于列表的记忆不因此不存在。`semantic-index.ts` 目前只给记忆的 `description` 建向量索引，正文修改而描述未变时还会复用旧向量；这是待修正的代码现状，不是目标契约。目标是只以 frontmatter 的 `summary` 为语义检索依据，正文交给 `brain_grep` 文字搜索；结果仍按记忆显示路径、`description`、`summary` 和可用的争议标记，再由模型按路径读取完整记忆。缺少摘要的记忆不参加语义检索。`semantic-discovery.ts` 当前只取相似度前 10 条，未设置“足够相关”的阈值；低相关候选也可能出现，前 10 外仍可能有相关记忆。它的 `truncated` 来自结果打包过程，没有向模型说明有多少条记忆排在前 10 之外。对较弱模型而言，“返回了结果”和“没有看到目标”都容易被赋予过强意义。仅按摘要检索的具体改造见 [13 · 摘要语义发现](13-body-semantic-search-design.md)。

## 3. 搜索规则：从主观缺口改为可观察触发

11 中的句子“已有路径和线索仍不足时才搜索”适合作为高层目标，不能独自承担较弱模型的执行规则。候选顺序如下：

1. **固定入口先读。** 本轮 Core 明确列出的适用路径、已经知道的准确路径，直接用 `brain_cat`；返回 `next_offset` 时续读。描述和路线不当作正文。
2. **没有当前事项的具体路径时发现。** 用户要继续先前工作，或要判断、改变现有项目的行为、接口、规范、设计时，先看 Core 和已读正文是否给出当前事项的决定、约束或续作记忆的准确路径。有就直接读；没有且本轮暴露语义搜索工具时，在形成重要结论或改动前作一次聚焦搜索。通用工作方法的路径不等于当前事项的历史路径。即使当前代码、文档、测试互相一致，也不能由此跳过这项检查。这个条件仍需人工观察是否过宽或漏掉相关记忆。
3. **当前材料独立足够的任务跳过发现。** 例如仅改写用户本轮给出的短文、简单计算、回答无需历史状态的一般问题；仍使用已经呈现且适用的 Core 和候选。这里按任务依赖的材料区分，不按消息长短区分。
4. **把工具选择压成清楚的分工。** 有准确路径用 `brain_cat`；未知路径、要按意思找过去认知且本轮暴露 `brain_ask_search` 时，默认调用它。明确要找正文中的词句用 `brain_grep`；要枚举路径模式用 `brain_glob`。语义搜索 query 写“当前对象／动作＋要找的历史决定、约束或经验”，不机械复制用户原话。工具返回不可用错误时按可用线索改用其他发现工具，并报告仍无法取得的重要内容。这个分工也与 [v7 的检索推导](05-design-derivation.md) 一致：模型只决定自己要找什么，不负责选择内部检索算法。
5. **候选须确认。** 只读取与当前对象和条件可能相关的结果正文；搜索为空、截断或工具不可用时，检查已覆盖范围与可用线索。摘要遗漏细节或旧记忆无摘要时，`brain_ask_search` 可能漏掉它；若缺失内容会改变当前行动，按具体词句、名称或路径线索改用 `brain_grep`／`brain_glob`。没有线索时说明受影响的判断并继续其他工作；不把一次有限检索说成“Brain 没有相关记忆”。

上面仍有模型判断，但把最易漏掉的“要不要发现历史认知”改成了任务表面触发。它不要求每轮搜索，也不让模型先证明自己信息不足。固定路线、当前用户消息和真实项目资料继续是判断的其他输入。

### 供逐字审核的中文候选

```text
先按本轮 Global Core 和当前 Project Core 的适用路线读取准确正文；同一任务可触发多条。已知准确路径时直接调用 brain_cat，返回 next_offset 时继续读取。路线、描述和搜索结果都只是找到正文的线索。

如果本轮要继续先前工作，或要判断、改变现有项目的行为、接口、规范或设计，先查看 Core 和已读正文是否给出当前事项的既有决定、约束或续作记忆的准确路径。有就直接读取；没有且本轮暴露 brain_ask_search 时，以“当前对象和动作＋要找的过去决定、约束或经验”作一次聚焦搜索。通用方法的路径不算当前事项的历史路径。只依据本轮材料即可完成、无需先前决定或项目状态的任务，可以跳过这次搜索。

brain_ask_search 只根据 summary 找候选；已知正文词句用 brain_grep。相关结果要用 brain_cat 读取正文和当前争议，再按其成立条件使用。没有命中、结果截断或工具不可用时，只能说明这次已检查的范围；旧记忆缺摘要也可能被漏掉。缺失内容会改变当前行动时，继续用可用的路径或文字线索查找，或说明具体缺口。
```

工具说明还要就近补清：目标实现只用 `summary` 做语义发现，按记忆返回有限的路径、`description`、`summary` 和可用的争议标记；排序和摘要不判断当前适用性。明确词句在正文里时用 brain_grep；枚举路径模式时用 brain_glob。通用段只保留何时进入发现，具体边界由对应工具描述拥有。改造完成前，不能把这段目标描述写进生产工具定义。

这段搜索文字仍是候选，不直接替换 08 或 production。它可能把已有事项路径误认作覆盖了全部相关决定，也可能让模型跳过兼具多个任务类型的专项正文。人工使用应观察实际调用、耗时、候选噪声和目标结果，再决定搜索范围；不能只数搜索次数。

### 3.1 保存规则：让较弱模型识别动作时机

“用户说可以就记录决定”与“形成以后仍需使用的认识时保存”都不足以指导较弱模型。前者可能把继续讨论误记成方案批准，后者依赖模型预测未来，容易同时产生漏写和滥写。用户纠正、确认、新要求、取得可复用认识或出现续作需要，只是**检查是否需要维护认知的信号**。先结合相邻讨论、仍有效的目标和当前事项恢复表达的指代、确认程度与范围；对可查的事实、原因及模型推断按用途取得依据。然后判断遗忘是否会使后续判断、执行或续作受损，再查同一认知并决定保存、修订、标记争议或不写。用户拥有的目标与取舍需要正确理解其范围，可查证的事实不能仅凭用户说过就升级为现实。

进入维护时，只记录当前能支持的结论、条件、依据和未解之处。每次 archival 写入或更新都按正文填写并核对 `description`（何时读）与 `summary`（记录了什么及边界）。这是模型可见要求，不把缺摘要升级为新的写入校验门槛。保存操作失败时说明未保存的部分与可行下一步，继续能完成的用户工作。候选运行时文字已放在 [08](08-model-facing-and-memory-text-draft.md)；人工使用需分别观察漏写、滥写和错误固化。

本次讨论链给出直接反例：“可以，继续”通常只推动当前讨论；“可以。继续。直到下一步是真正修改”也没有批准尚未展示的完整生产 Prompt。“改造完成后单独给旧记忆补写 summary”则明确改变了实施顺序，应进入 v7 实施方案；“顶尖全能人才的 Base 没了吗”要求先回看原始表达和 Base，再决定如何修正长期目标的记录。这些判断来自话语指向和上下文，不来自某个词本身。

外部资料支持这个方向，但不直接证明本稿的触发词有效：[Anthropic 的 Agent 上下文工程文章](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)建议用清楚、具体且不过度复杂的指令，并描述长任务中保存关键状态与依赖的做法；[OpenAI 内部数据 Agent 的案例](https://openai.com/index/inside-our-in-house-data-agent/)把难从其他资料推回的用户纠正、过滤条件和约束作为记忆价值的例子，同时在资料过时时查实时来源；[LongMemEval](https://arxiv.org/abs/2410.10813)把信息提取、知识更新与无依据时不作答列为不同的长期记忆能力。上面的保存触发仍是依据 Brain Base 与当前工具边界提出的候选，须由用户在真实模型使用中检验。

## 4. 工具可用性是独立的硬前提

当前 `runBrainMcpServer` 按全局配置选择是否注册 `brain_ask_search`；`createProductionBrainServices` 初始化语义运行时失败时会返回没有 `semantic` 的服务。`restoreProductionBrainContext` 为 hook 注入上下文时还显式传入 `initializeSemantic: false`，而 renderer 依据配置的 `features.semanticSearch` 决定是否显示主动搜索段。因此“配置启用／工具被列出／本轮真的可运行”可能是三个不同状态；工具被调用后可以返回 `semantic-search-unavailable`。这是代码路径推导，需工程验证不同宿主的具体呈现，不应让较弱模型独自推断原因。

较弱模型友好的契约至少要做到：本轮文案只承诺实际支持的能力；工具失败返回明确可执行的退路；不能把语义依赖安装完成等同于搜索已可用。实现方式仍需在能力与 Prompt 审核后确定，不为此先建新的健康服务或安装框架。

## 5. 默认包入口与正文的分工

用户确认的安装形态是复制三份 Global memories，只给 Global Core 加一行。它提供明确、准确的 `brain_cat` 下一动作；较弱模型仍可以完成这类直接指令，不需要因“理论上可能漏调”就引入自动展开正文或额外的包注册机制。[Base](../base/02-design-philosophy.md) 要求照顾较弱模型，重点是不要让它补出隐藏的判断链，并非把所有明确的工具动作都移交给 runtime。

静态检查应确认入口文字直接、路径真实可读、工具暴露、分页能够取得所需正文。人工使用再观察实际读取和应用。若以后确有漏读证据，先区分路径／宿主故障、文字含糊和模型行动问题，再决定是否需要改变机制。当前自检不能以假设的漏读为由推翻已确认的一行 Core 入口。

### 与 Base 的高水平通用思考目标对照

[Base](../base/01-origin-and-goal.md) 要求从顶尖通才的实际思考能力反推模型、Brain 与 Harness 的设计。当前候选包的 `core.md` 已覆盖可修正的目标理解、证据边界、主动取证、行动反馈；本轮又把“熟悉方法何时可直接用、异常或冲突时何时展开机制并比较解释”写入候选正文。这些是把 [通用认知研究](02-generalist-cognition-research.md) 中的问题表征、监控、动作选择与反馈关系翻成模型可执行文字的尝试。

仍未得到保证的是：较弱模型是否会在未被显式告知“这里有异常”时发现旧模式失效，是否会选择真正能区分解释的证据，以及能否把新结果用于修正原先的问题理解。稳定入口、领域读取范围、实际工具与结果反馈必须共同承担这些失效；不能只因包正文包含正确原则，就声称系统已实现 Base 的目标。人工验证应看模型的实际选材、取证、行动和修正，而不只看它是否复述了原则。

## 6. 给用户人工使用的成对场景

每组记录：本轮实际注入、暴露的工具、Core 路线是否读取、搜索是否发生、候选是否 `brain_cat`、结果怎样影响行动，以及耗时／多余调用。保持同一模型和工具条件，一次改变一个影响判断的条件。

| 场景对 | 应看到的区别 | 主要归因位置 |
|---|---|---|
| 本轮提供短文改写／现有项目新增模糊功能 | 前者无需主动历史搜索；后者读项目路线和软件正文，再查既有决定与约束。 | 搜索触发与专项路由 |
| 全新且自足的请求／未说“延续”但用户长期目标会改变方案的模糊请求 | 前者可以直接处理；后者应从当前对话、Core 与候选发现过去取舍，缺准确路径时检查是否需要语义发现。不能仅因没有“继续”二字就把长期目标当不存在。 | 初步意图理解与 Global 认知发现 |
| 给出准确记忆路径／只说“延续之前那个方案” | 前者准确读取；后者结合 Project 路线，必要时语义发现，不能凭最近候选猜唯一工作。 | 路由、查询与候选选择 |
| 旧规范、代码、测试一致／另有当前用户决定或运行反证 | 都查材料适用范围；后者不能让旧材料压过仍有效的新决定或当前观察。 | 正文应用与来源判断 |
| 语义搜索返回高排名但无关结果／相关结果在前 10 外 | 前者不套用；后者不能因一次未见目标就声称不存在。 | 检索结果呈现与模型判断 |
| 搜索正常／已配置但运行时不可用 | 正常时读适用正文；不可用时给出明确错误和可行退路。 | 宿主、工具与失败文案 |
| 只需软件方法／同时修改代码和可执行 Prompt | 后者同时读取软件与可执行文本正文。 | 多路线触发 |
| 用户确认今后都按某项约束处理／只让模型本轮换种措辞 | 前者保存或更新有效决定，后者完成当前输出即可。 | 保存触发与范围 |
| 查明了可复用的故障条件／只是提出一个待查原因 | 前者按证据和成立条件保存认识；后者若需续作，仅保存待验证状态。 | 事实、推断与续作 |

静态审查能指出链路和契约缺口，不能给出某个弱模型的成功率。用户人工验证后，按失败发生在注入、路线、工具、候选选择、正文理解或最终行动的哪一环修订；不把所有失败都归咎于搜索提示词。

## 7. 建议的最小实施顺序

1. 保持 `brain-ai` 的三份正文和 Global Core 一行准确入口；静态核对路径、frontmatter 的适用条件和跨任务同时触发的软件／可执行文本路线。这里不增加包专用的自动展开机制。
2. 以 [08 的中文候选](08-model-facing-and-memory-text-draft.md) 为整段审核对象，合并 renderer 与 `brain_ask_search` 工具描述中的触发规则，删掉“启用后每轮搜索”。宿主 hook 只保留宿主确有的绑定与诊断，避免另一份通用规则。
3. 把语义搜索的输入改为 archival 的 `summary`，继续按记忆返回路径、`description`、`summary` 和可用的争议标记。摘要变化更新向量与候选展示，描述和争议状态变化更新结果元数据；正文仍由 grep 和 cat 取得，不增加正文片段索引。结果应说明仅覆盖有可用摘要的记忆，并区分前 10 排名截止与输出字节截断。代码改造完成后另做一轮旧记忆摘要补写。细节见 [13](13-body-semantic-search-design.md)。
4. 核对功能启用、工具暴露、实际运行时和失败返回的关系。若工具暴露但运行时缺失，错误要让模型知道可改用哪些已有线索或准确路径；renderer 不把配置开关写成可运行保证。
5. 用户按第 6 节的成对场景人工使用后，再依据真实失败决定是否调整默认搜索范围、摘要写法或候选数量。评估不能只看工具调用次数，还要看是否找到并正确使用影响结果的认知，以及该保存的认识是否被保留、临时猜测是否被错误固化。

第 2–4 步涉及 production Prompt、工具或 runtime 的修改，仍受完整文字审核与明确批准的 Gate 约束。本节是待讨论的实施次序，不表示已经获准动代码。
