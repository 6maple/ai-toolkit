# 09 · 真实场景与最小改动复核

> 2026-09-30 状态注记：本页部分“三份正文 / 软件与可执行文本”的表述记录的是当时审查阶段。当前 `brain-ai` 已扩为五份正文，并拆出普通用户表达与正式报告写作；当前完整正文以 [10](10-default-memory-pack-design.md) 和 [16](16-model-facing-composition-review.md) 为准。

本文复核 [07 的改造方案](07-code-and-cognition-change-proposal.md) 和 [08 的中文正文](08-model-facing-and-memory-text-draft.md)。用户要求对整个方案采用同一标准：从实际场景和当前实现出发，判断问题是否存在、由谁解决、最小改动是什么；没有证据时保留待定。模型实际执行效果由用户人工验证，本文只做静态核对和场景推演。

## 1. 已确认的约束与尚未证明的设计

已确认：`brain-cli` 放在 `code/brain-cli`，用仓库内 `brain: "link:../brain"` 调用 Brain 导出的原子能力；CLI 自己组织 Agent 的 Brain MCP 安装／更新、记忆导入与 Global 导出、语义搜索安装／更新及可选记忆包安装。顶层 `install/update` 只针对 Codex、Claude、DSH 等 Agent 的 Brain MCP 接入，用 `--agent` 选择宿主，本地代码和 GitHub 两种来源均由参数显式输入；记忆包没有更新命令。导入先查冲突，冲突则失败；导出保留相对路径，损坏的记忆状态给警告并继续；现阶段不集成 Web。用户明确：默认包的正文要从真实需求重新设计，`ai-think` 只作参考；安装时按相对路径复制到 Global memories，目标 Global Core 只加一行入口。production Prompt、工具和当前用户 Brain 正文仍须展示准确文字、审核后再改。

尚未证明：每轮必须调用语义搜索、新设计的软件领域记忆能改善旧材料问题、活跃工作必须有独立登记、记忆导出必须有 `manifest.json`、GitHub 来源必须指定 tag／commit、四个宿主的全部上下文需要逐字相同。这些可以是候选，不能由一个场景或现有代码直接推出。首包的物理位置已确定为 Global memories；具体候选正文见 [10](10-default-memory-pack-design.md)。

## 2. 用不同类型的真实任务查上游失效

| 场景 | 容易出现的错误 | 当前可用依据与最小动作 | 仍需观察 |
|---|---|---|---|
| 用户模糊提出新功能，旧规范、代码和测试一致 | 把旧系统当前行为当成新目标；或替用户选择影响行为的解释 | 读取仍有效的决定、旧资料形成条件、实际入口与调用方；把几种会改变结果的解释具体化，查完可查事实后请用户裁决真正未定的取舍。现有软件记忆已经区分需求、实现和测试的职责。 | 模型是否真的按路线读到领域方法，是否停在正确的用户决定边界。 |
| 用户明确要求局部修改 | 为每处普通行为变化都重新请求许可，或无限扩大调查 | 在已授权范围内读取受影响入口、规则和必要验证后执行；只有超出授权或存在会改变结果的未决取舍才请用户裁决。 | Root 的协作文字是否造成普遍停顿。 |
| 用户给出新的纠正，旧记忆仍有部分有效 | 用较新的材料整份替换旧决定，或无视纠正 | 判断新证据实际涉及哪个对象、条件与结论；只更新受影响认知及描述，保留其他有效约束。 | 工具描述和记忆正文是否让模型识别“同一认知”的边界。 |
| 检索无命中、截断或工具不可用 | 把有限结果当成不存在；把接线故障归咎于 Prompt | 已知路径直接 `brain_cat`；没有路径时查看搜索范围、截断、可用工具和真实错误。当前路由回放只观察到一次正确选路，随后工具未能读到正文。 | 故障究竟在发现、路径、宿主绑定还是模型行动。 |
| 任务跨相关项目 | 将相关项目的记忆或 Core 当成当前项目的规则 | 相关项目普通记忆按需发现；真正要读取／分析其文件或根据其状态决策时，读取对应 Core。现有 renderer 已提供这条边界。 | 宿主提供的项目映射是否真实、相关 Core 是否可读。 |
| 旧测试全绿，用户的新结果未达 | 以旧验收证明新功能完成 | 区分旧测试覆盖的条件、新目标和实际运行结果；只补受影响的验证。 | 是否有真实运行反馈，不能只审 Prompt。 |
| 多项工作并行且跨会话续作 | 被动候选最多 10 条，某项工作没有稳定入口 | 现有 Global／Project Core 原文进入每轮上下文，可先在 Project Core 保留每项需默认续作的准确路线和正文；迁移后检查路径可读。 | 真实并发或故障是否产生常见断链，是否需要结构化登记。 |
| 新用户选择安装默认记忆包 | 覆盖既有 Core／记忆，或把当前用户的个人方法误作通用默认 | 先审核重新设计的包正文；安装时检查全部目标冲突，复制包文件并向 Global Core 加一行入口。 | 复制结果、内部引用和 Core 入口是否准确可读；小任务是否保持轻量。 |
| 导入／导出 Global 记忆 | 路径冲突或损坏状态造成静默覆盖／争议说明丢失 | 导入检查文件路径与内容冲突后写入；导出保留 `global/...` 路径和可用的状态，状态异常警告并继续。 | 现有 companion 文件怎样最少复制、并发修改时怎样报告已写入部分。 |
| 本地或 GitHub 安装 Brain MCP | 现有插件文件包含 checkout 的绝对命令路径，在另一机器不能直接运行 | 两种来源都显式指定；安装时根据目标机器实际生成接线文件并报告来源、目标与需要的宿主信任步骤。 | 各宿主目前支持的安装入口和可移植安装物形式。 |
| 语义搜索安装或更新 | 依赖健康但功能未启用，或模型看到不存在的工具 | 现有脚本已有 Python、模型和健康检查；迁入 CLI 后复用这些行为，CLI 明确报告配置与重启要求。模型只看到实际暴露的工具。 | 是否需要改变当前“理解任务后每轮搜索”的策略，不能由安装成功推出。 |

## 3. 各部分的修订判断

这些问题有共同的推导错误：把“正确目标”直接跳到“必须新增一个机制”，中间没有确认现有能力能否完成、失败发生在模型判断还是工具接线、文字应该由哪个位置拥有。例如“Root 需要及时被看见”不直接证明“整段必须放 Core”；一行 Core 路由是已确认的安装形态。“多项工作需要续作”不直接证明“必须建登记表”；“状态不能无声丢失”不直接证明“导出必须做清单文件”。每次增加机制前，先写清可观察的失败、现有路径的边界和新增机制要改变的结果。若现有方法已经写明原则，则先查实际执行链是否断在入口、读取、理解还是验证，避免把同一规则再写一遍。

### Brain Prompt 与工具文字

每轮确实需要提供 Global／当前 Project Core、候选的来源和状态、准确读取方法、实际可用的工具。当前 renderer 已有大部分内容；因此先对齐重复和矛盾的句子，不把 08 的整段新协议直接替换现有实现。工具使用条件、参数、返回与副作用应贴近对应工具；可选思考方法属于记忆包。`brain_think` 当前会推进辅助学习状态并尝试 Git checkpoint，故“只读”不能作为其描述；普通文案称“建立本轮工作上下文”更准确。失败后是否重试应按实际错误与副作用处理，不能单靠“每轮恰好一次”概括。

08 的“理解任务后调用 `brain_ask_search`”沿用了当前实现，但不是由所有场景证明的产品需求。已知准确路线时再做一次广泛搜索会增加调用与噪声。更合适的候选是：**“当前路线、已知路径和材料仍不足以找到可能影响行动的相关记忆，且该工具实际可用时，使用 `brain_ask_search`；搜索结果是候选，重要内容仍按路径读取。”** 具体触发强度交由用户观察。

08 原先的协作研究候选有过宽风险：“方案会改变用户可见行为，实施前等待用户回应”可能覆盖已授权的普通功能修改。新包将关键边界直接写入必读入口：模型自行调查事实、承担专业设计；重要方案向用户说明以便纠正；仍缺用户拥有且会改变重要结果的选择时请用户裁决；已有决定和授权按其范围继续。完整候选见 [10 的 `core.md`](10-default-memory-pack-design.md#memoriesskillbrain-aicoremd)。这仍是待审核正文，不是已批准的包内容。

### Root 的位置与记忆包

当前 `@global/core.md` 只放最小读取引导；`brain_edit` 描述也要求 Core 保持简短路线。08 曾把整段 Root 放入 Global Core，会改变现有约束并增加每轮长度。新包的候选形态是三份重新设计的 Global memories，Global Core 只增加指向 `brain-ai/core.md` 的一行；包入口直接包含跨任务的关键判断方法，软件与可执行文本方法按任务类型读取。现有 `ai-think` 和研究文档的 Root 文案可供对照，但不直接复制进新包。是否存在模型读不到或读了却未执行的重要失效，由用户人工使用观察；若有，再定位并讨论相应改动。

此前把用户确认的“安装形态”解释成“原样复制当前 `ai-think` 正文”，是错误推断。可选安装仍要求包内容本身适合成为默认方法。新包须先逐字审核，安装器只复制经审核的文件，不做内容筛选；用户已经安装的记忆由其 Brain 维护。CLI 顶层“安装、更新”仅指 Agent 的 Brain MCP 接入，记忆包只安装。

### 软件领域记忆与当前用户 Brain

当前用户的 `ai-think/software/core.md` 已区分需求、公开契约、测试和实现各自能证明什么。这可作为对照：新包要覆盖“旧材料一致但共同过时”的场景，却应从任务需要独立写出简洁正文。10 给出软件候选；实际使用若仍发生旧材料压过新目标，再定位是没读到软件方法、读到却没执行，还是当前资料本身不足，再决定改路线、改正文或补真实取证步骤。也不把“法律”作为所有软件任务的默认外部检查项。

08 建议压缩当前 Project intention，但 live 正文包含阶段限制和实验边界。只有核对每条当前仍有效的决定、争议、证据路径和后续入口后才能压缩；“研究文档里还有”本身不足以证明新任务仍会准确读到它们。相关项目 scope 文字若确实过时，可只改已失效的句子。当前用户的具体读取和表达偏好继续由其自己的 Brain 拥有。

### 活跃工作与 CLI

Project Core 已经作为稳定入口出现，被动候选的 10 条和 8192 字节上限不应承诺承载所有活跃工作。眼下先用正文先写、Core 再加路线、核对可读的简单步骤。结构化登记、联合写入和完整索引只有在实际数量、并发和故障证明当前做法无法兑现“跨会话续作”时再设计；不能先把所有未来 work 注册成一个新系统。

CLI 的确定需求是命令责任与可观察结果。导入的“整批先检查冲突”表示发现已存在的不同内容时不开始写，不能未经实现就声称整个批次具有数据库式原子性；若写入中断，应准确报告已完成路径。Global 导出可先沿现有文件布局复制正文和有效配套状态，异常警告，不先假定需要 `manifest.json`。记忆包安装只需检查目标文件和一行 Core 入口的冲突、复制缺失文件并报告结果；它与 Agent 的 Brain MCP 安装／更新、语义搜索安装／更新以及 Global 导出分别对应不同命令。

GitHub 安装需要明确仓库来源，并在执行时确定实际取得的版本；`--ref` 是否必填属于 CLI 易用性选择，用户只确认“来源作为参数输入”。`link:../brain` 是仓库构建关系，不使现有 checkout 专属插件自动变成跨机器安装物。各 Agent 的接入和信任步骤先以现有插件实际支持为准。语义搜索脚本迁入 CLI 后保留其健康检查与配置边界，暂不增加独立服务管理层。

## 4. 再按早期讨论检查关键设计思想

### 以高水平通用思考为主目标复核当前方案

[Base](../base/01-origin-and-goal.md) 的目标落到真实任务，应观察模型能否形成可修正的问题理解，找出当前最影响正确行动的缺口，从适当来源取得依据，选择合适的沟通、调查、分析、设计或验证动作，并随结果修正。只会复述这些词，不能算达到目标。[02 的人类认知研究](02-generalist-cognition-research.md)为这条关系提供参考；模型能否稳定执行仍待用户人工验证。

| 当前方案的部分 | 对目标的贡献 | 本轮审查 |
|---|---|---|
| 每条新消息的 Brain 上下文、Global Core 一行准确入口、可选 `brain-ai/core.md` | 在用户安装包且宿主交付成功时，稳定把通用方法带回模型附近；专项方法从正文按任务进入。 | 这是方案最重要的可行基础。入口可读、模型实际读取和应用是三个不同的观察点，不能由第一点推出第三点。 |
| `brain-ai/core.md` 的初步理解、材料证明范围、经验条件、取证与反馈 | 覆盖问题理解、审慎用经验、广义取证和修正。 | 主要关系已在场；当前几段文字分别描述做法，但没有在“选择下一步”处直接说明怎样按当前最关键的缺口选动作。较弱模型可能正确复述原则，却仍继续第一条熟悉的工作路线。 |
| `software.md`、`instructions.md` 及领域覆盖 | 在软件和可执行文本任务中提供较具体的来源与完成条件。 | 对这两类任务有明确入口。其他领域先依通用方法和已有用户记忆工作；只有实际任务暴露可复用的领域缺口时再设计相应正文。三份文件本身不能代表“全领域专业能力”。 |
| 历史 cognition 的准确路线和主动发现 | 让过去目标、决定、条件与经验进入本轮问题理解。 | 当前搜索候选主要由续作和现有项目触发；没有这些表面特征的新任务，也可能需要用户长期取舍来形成正确问题。应先在通用思考方法中说明如何识别这类历史信息需要，再核对 Brain 搜索文字的触发条件。`brain_ask_search` 不能代替当前 repo、运行结果或外部资料。 |
| 结果反馈与认知维护 | 用真实结果改变受影响的判断和长期记忆，逐渐减少重复犯错。 | 正文已说明反馈修正，Brain 的读取、编辑与争议机制承接长期部分；目前只有静态方案，尚无证据证明较弱模型在跨轮任务中稳定形成这个循环。 |

最小的下一步应先审一段**通用方法正文候选**，而不是先扩大语义搜索调用范围：

> 需要决定下一步时，先看当前最影响正确行动的是什么：用户想改变的结果仍不清楚、关键事实还没有从相应来源取得、现象的原因尚未查明、几个方案的后果需要比较，还是已有产物缺少真实结果验证。按这个缺口选择下一步：恢复相关对话和过去决定、调查项目或外部现实、比较能区分解释的证据、形成可纠正的方案，或检查实际结果。进入专项工作后，按相应方法要求的材料和验证条件判断，不凭“我觉得够了”跳过。取得新信息后修正受影响的理解，再决定继续行动还是转向另一种方法。小而明确且依据足够的任务直接完成。

这段只把当前候选正文已有的关系放到模型选择动作的位置，不提出一个新的角色系统或运行时控制器。用具体任务检查：新会话中用户只说“想做一个 app”，模型应先理解目的并检查已知的用户长期目标，当前搜索触发可能漏掉这一环；旧事故似乎解释当前故障时，应先取得当前运行证据，不能因存在 Brain 记忆就优先套旧原因；明确且自足的小任务应直接完成。审查重点是能否产生正确的下一动作、是否引发多余调查，以及有无要求模型凭主观自信判断资料已足够。审查通过后，再据此修订包正文与搜索触发；模型实际行为由用户人工验证。

归档讨论中的用户消息 0305、0313、0321 明确区分了三件事：每轮把适用的思考方式带回模型可用的近期上下文；同一项目可有多项并行工作；Brain 本身应能供不同 Agent 宿主使用。这些要求在 v7 的每轮建立、可选方法包和按事项续作中已有设计承接，但此前 Base 对它们只作笼统的“恢复 cognition”表述。现已在 [Base 的根问题](../base/01-origin-and-goal.md) 补回原始诉求。可选包未安装时，不能声称 Brain 已向模型提供包内的通用思考方法；本轮注入成功也不证明模型实际按方法行动。

用户消息 0001、0096 还强调：模型先根据用户表达与上下文形成足以决定检索方向的初步理解，再主动寻找可能改善该理解的过去认知。检索本身也可能改变对用户意图的判断，因此不能把“完全理解用户”写成搜索前提。后续用户接受有路径先读、线索不足再搜索的方向；本轮只把“初步理解可在取证后修正”补进候选正文与查询参数，不恢复无条件每轮搜索。当前搜索触发主要覆盖续作和现有项目；新任务若未显式说“延续”，但确实依赖用户长期目标或过去取舍，仍可能漏掉 Global 历史认知。这是需用真实案例检查的剩余边界，不凭空增加每轮搜索规则。

用户随后明确了摘要写入的取舍：模型可见的 `brain_write`、`brain_edit` 说明直接要求每次填写并核对 `summary`，像“立即读取准确路径”一样清楚表达动作即可；不因假设模型会漏填而增加写入拒绝、额外检查或新机制。缺摘要的存量记忆仍按已确认顺序单独补写；摘要搜索本身只覆盖确有摘要的记忆，这一事实继续如实呈现。

早期的“按阶段进入不同角色”在 [高水平通用认知研究](02-generalist-cognition-research.md) 中已继续追到更上游的判断：当前问题和依据变化时选择相应的调查、沟通或执行方法，不把角色固定成一套人格或线性阶段。候选 `brain-ai` 原先主要按软件／可执行文本类型路由，对“用户先说想做一个 app，却还未说清所解决的问题”缺少就近动作；现已在通用正文增加“先把做法当候选，查明现状与想改变的结果，必要时让用户纠正，再随证据转换工作方式”。这仍是待人工验证的候选文字，不宣称已实现角色切换能力。

其余曾被担心的要点已有明确归属：高水平通用思考作为用户目标进入 Base；外部资料、运行结果和项目事实由模型借助相应工具取得，Brain 不冒充唯一事实源；重要内容需要正文与成立条件，摘要及搜索命中只是候选；Brain 或宿主失败时向模型说明具体缺口并继续可做的工作。这些不因本轮复核而重复写成另一套 Prompt。

### 多轮讨论中怎样沿用模型已经说明的判断

用户提出：让模型把自己的判断讲出来，能否减少下一轮重复理解。这里有实际收益：当目标解释、关键依据或方案取舍会影响下一步时，简短说明当前判断，用户能够及时纠正；之后的模型也能在对话中找到一个明确的工作结论，接着新信息修订它。即使用户未回应，这段话仍只代表模型当时的判断，不能当作用户已经确认的决定。

这项收益有边界。后续轮次已有对话可用，但长对话压缩、跨会话或没有正确注意到旧结论时，单靠说出来不能保证恢复。跨会话仍需继续的工作由 active-work intention 保存目标、已确认基线、当前进度、未决问题和下一步；长期有效的用户决定与经查证的认识各归其记忆 owner。对话里的暂定判断、用户确认的选择和已验证的事实不能混写。说过的判断若被新证据或用户纠正改变，应说明受影响的变化，继续沿用其余有效部分。

前一版审查把“讲出判断”理解为仅在重要节点才出现。用户明确纠正了这个范围：参考 `ai-think/core.md` 每回合展示完整高层工作路径的做法，**每次把当前理解和整条路径放在开头相邻两行**。路径让用户和后续轮次知道已走到哪里、下一步怎样抵达结果；第一行让用户看见模型目前怎样理解任务。尚未取证的理解应标为暂定，小任务压缩路径节点；这些边界用来控制噪声和锚定，不能据此取消每轮两行。

修正后的 `brain-ai/core.md` 候选补充：

> 每个用户回合开始，在第一条可见消息里相邻两行写出“理解：当前任务、目标和边界”和“路径：`任务起点 → 【当前节点】 → 任务完成或明确交接`”。路径遵循当前任务的实际工作方式并覆盖整个任务，节点数按需要决定，小任务可压缩；后续重要判断改变时解释依据与变化，更新受影响的理解和路径。模型说过的判断仍是模型判断，用户只在明确确认的范围内作出决定。

用户先对“讲出判断以便续作”的方向回复“可以”，随后明确其完整要求是上面这两行。用户再澄清：`x → 【y】 → z` 只是在指出整条路径需要用 Markdown 反引号包住，不能据此限制为三个节点。修正后的文字已并入 [10 的 `brain-ai/core.md` 候选正文](10-default-memory-pack-design.md)。跨会话保存的判断方法由包或用户记忆指导，Brain 工具和活跃路线承载已保存的状态及读取入口。本轮只是校正设计候选，完整 production Prompt 仍待审核，也不引入新的记忆类型、字段或逐轮记录机制。人工验证可对照模糊目标、明确小任务、后来纠正及跨会话续作四类场景，分别看是否有帮助、是否产生多余说明或错误继承。

### 剩余设计问题：下一步动作、历史发现和续作保存

回到 Base 的“做对做准／自主省事／高水平通用思考”检查 [10](10-default-memory-pack-design.md)：必读正文原先要求形成可修正的理解、查材料的成立条件和接受反馈，但未在“选下一步”处直接把当前主要缺口映射到动作。较弱模型可以复述原则，却仍沿最熟悉的路线继续。用户认可这一修订方向后，已在 `brain-ai/core.md` 候选中写入目标未明、事实未取、原因未辨、方案后果未比较、结果未验证与相应动作；复杂问题补充现状、目标和可改变结果的环节。小任务可直接完成，这些情况不构成固定阶段门禁。具体措辞仍待审核。

[08 的搜索触发](08-model-facing-and-memory-text-draft.md)原先主要写续作和现有项目。另一个真实场景是用户提出一个新做法或请模型替自己规划，当前消息缺少会改变方案的目标与取舍，但过去 Global cognition 可能已有这些信息。用户认可这一方向后，已在有、无 `brain_ask_search` 的两个候选分支中加入这一入口；无准确路径时按可用工具聚焦发现，新材料指出另一项具体历史需要时可再查。自足任务可跳过。`brain_ask_search` 仍只按 `summary` 找候选，正文靠 `brain_cat` 与文字 `brain_grep`；有限结果不证明不存在。具体措辞及过度调用风险仍需审核。

[08 原先的保存段](08-model-facing-and-memory-text-draft.md)以“工作需要跨消息继续”作为检查信号，可能使较弱模型把同一会话的普通进度也当成持久化目标。用户认可修订方向后，保存方法转入 [10 的可选包正文](10-default-memory-pack-design.md)，以跨会话继续和遗忘后果判断是否值得写入。每轮两行承担当前会话的显式定位，不等于已经保存可跨会话继续的状态。

示例仅放在模型需要区分动作的位置：[10](10-default-memory-pack-design.md) 展示小任务与续作任务的两行格式、旧报名规则与候补功能，以及临时步骤与跨会话续作的保存区分；[08](08-model-facing-and-memory-text-draft.md) 展示依赖过去目标的新规划与自足改写任务的读取区别。例子用于校准条件、判断和动作，不独立制定规则；其数量和措辞仍按模型可见正文审查，实际遵循交给用户人工验证。

用户随后明确排除可选包与已有方法记忆的并存告知：安装者自己查看已有记忆。CLI 仅处理目标路径、包正文及 Core 入口的冲突，不增加跨记忆语义检查或并存提醒；现有其他路线保持原样。

这三处属于模型可见文字的待审核语义。CLI 来源与宿主安装物、摘要索引、活跃工作路线和工具错误的当前实施候选在 [14](14-implementation-contract-review.md)；它们首先需要按真实接口与产物核对，不能因模型方法段有缺口就增加另一套控制器或通用安装框架。完整审核仍需把 08、10、15 合起来检查所有模型入口、工具条件和失败退路；模型实际效果由用户人工验证。
