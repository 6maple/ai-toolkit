# ai-toolkit 项目修改与审查

## 目标和优先顺序

从用户真正要取得的结果、当前项目现实和已确认设计出发，决定需要查什么、修改什么、怎样验收。模型负责专业调查、判断与执行；程序、工具和项目规范各负责自己能够可靠保证的部分。

先保证**正确、清楚、低歧义、能力较弱的模型也能执行**，再优化文字长度、读取量、调用次数及实现成本。已确认的目标、具体条件、方法和授权边界，与历史候选、模型推断及旧文档分别辨认；新资料影响旧判断时修订真正受影响的部分。

## 按任务读取方法

- **每次实质设计、审查或修改**：读取 [设计依据、资料与记忆](references/evidence-and-design.md)，恢复本事项有效背景、目标、证据及现实。
- **编写或审查任何模型可见指导**（Prompt、Skill、Tool 描述、AGENTS、Brain 记忆方法等）：同时读取 [模型引导写法](references/model-guidance.md)。
- **涉及 Brain 的 step、State、Tool、宿主或认知/记忆配合**：同时读取 [Brain 工作流与契约](references/brain-workflow.md)，依据当前源码核对实际行为。
- **形成修改候选、实施修改、独立审查或交付验收**：读取 [修改审核与验证](references/review-and-verification.md)。

满足条件即读取对应 reference；本轮已经完整取得且未变化的内容直接使用。新的任务涉及另一模块时再读取它。全部引用只在本 Skill 入口维护，reference 不依赖本 Skill 的步骤编号，也不逐层引用其它 reference。

## 工作顺序

1. **查清本次目的和现状**：结合用户原话、相关记忆、正式规范、代码和真实结果，查明现象怎样形成、实际影响什么、用户要改变什么。区分需要用户决定的重要取舍和模型应承担的专业判断；确定本轮是调查、审查还是获准修改。
2. **调查并定验收**：默认把网络资料作为调查途径之一，核对当前专业实践、官方资料、版本及环境；决定不查须有具体理由。先明确本次应改变的真实行为、不能损失的已确认要求，以及实际如何验证。
3. **形成最小充分的方案**：从整体指导、调用与使用关系找到实际受影响的位置；每处变更说明真实依据、原有条件与新动作、对上下游的影响。由一次局部问题举一反三检查同类真实风险，不为假想问题扩大设计。
4. **修改前交用户审核**：集中提供**完整修改方案**，包括全部文件、准确位置、原文和拟改全文、每处理由、保留的语义、实施顺序、验收及恢复办法。用户审核对应具体内容与范围后才修改；方向认可不代替具体文字审核。
5. **按批准范围实施并验证**：先检查工作区与现行文件，保留其它有效内容；修改后回读全文与 Diff，检查实际功能、模型可见指导组合和真实结果。区别静态审查、工程测试、真实模型行为验证；未完成的验证如实记录。
6. **维护与交付**：把仍有效的新决定和关联修订维护在各自规范、Brain 记忆或事项工作记录中；同一要求优先在原位置修改，不累积重复版本。交付实际产物、验证依据、未完事项和必要续作入口。

普通工程任务沿同一目标、依据、授权与验证顺序执行；只在当前触发条件成立时读取 Brain 专项方法。子目录另有 AGENTS.md 时同时遵守其适用要求。
